### 公共接口

所有新增计算/命令返回 B0 的 Result；纯候选接口不会保存、安装正式状态或发事件。持有状态的模块使用与 Economy 一致的 `New(content)` 方式，测试可注入内容副本；正式使用统一 `data.content`。

| 模块 | 待实现接口与结果 |
|---|---|
| Letter | `InitialSnapshot()`、`ValidateSnapshot(snapshot)`、`GetSnapshot()`、`Restore(snapshot)` |
| Letter | `PlanReceive(state, letterId)`：已有实例时返回已有结果，首次生成收到的信件及队列候选 |
| Letter | `PlanMarkRead(state, instanceId)`：已读候选；重复阅读不再改变状态 |
| Letter | `PlanMarkCut(state, instanceId, spanId)`：已剪候选及从配置解析出的来源；重复剪裁返回已有结果 |
| Letter | `GetView(instanceId)`：自我介绍、正文片段/缺口、地址、位置和操作状态的副本 |
| Letter | `PlanArchive(state, followup)`：B0 归档记录的纯投影；本批只验证投影与幂等，正式确认由 B5 调用 |
| WordToken | `InitialSnapshot()`、`ValidateSnapshot(snapshot)`、`GetSnapshot()`、`Restore(snapshot)`、`GetInventory()` |
| WordToken | `PlanCut(state, source)`：词条状态候选与 token；source 使用 `wordId/sourceLetterInstanceId/sourceSpanId/sourceNpcId` |
| WordToken | `ResolveRecipe(state, recipe)`：校验已剪、可用与重复实例，返回定义/来源副本；不求药效，不扣词条 |
| WordToken | `PlanConsumption(state, resolved)`：按 reusable 生成确认消耗候选与明细；正式消耗属于 B5 |
| GameState | `ReceiveLetter({letterId})`、`ReadLetter({letterInstanceId})`、`CutWord({letterInstanceId,spanId})`：操作完整候选的统一命令 |

`GetView/GetInventory` 不触发已读、剪裁、保存或自动奖励。接口实现后将实际 value 字段、错误码与事件载荷写入模块注释和行动记录，复核双方调用点，保持 B0 的字段含义。

## 3. 按顺序实施

### P1：解析真实正文，建立稳定位置

新增 Letter 中的解析逻辑与 `debug/LetterTest.lua`。

- 从 `Data.GetLetter` 读取定义，`Data.GetWordByText` 对应 `{{词}}`；当前 Data 需先成功 Load。不要在系统写路人甲的正文或六个词名。
- body 中每个标记按原配置顺序生成 `body:1`、`body:2` 等，即使显示文本相同也有独立位置。位置不是中文字符偏移或 UTF-8 字节偏移。
- 视图用有序片段，例如普通文本片段和 `{spanId,wordId,text,cut}`；剪后保留该位置与缺口标志。再次打开使用原始定义加 cutSpans 投影，不删除正文后再给剩余位置重新编号。
- 原换行、自我介绍和地址均保留；正文解析不能把半个中文字符切开。UI 后续负责缺口宽度与样式。
- 校验未知词、空标记、未闭合标记与非法类型，报具体配置路径；直接回信显式不可剪，不能因没有 body/标记就误报普通订单信缺配置。

出口：真实首信得到六个稳定位置与三个文本区；重复词夹具的两个位置可分别剪；再次生成视图编号不变。

### P2：实现 Letter 状态与收到/已读候选

状态严格沿用 B0：`{byId,bottleQueue,directArchive}`；byId 条目为 `{letterId,senderId,received,read,cutSpans,claimedAttachmentIds}`。

- 阶段 1 同一订单信只收一次。信件实例 ID 使用确定性方案 `letter:<letterId>`，配置 ID 不当中文显示文本；未来允许同定义多次来信时另定实例序号，不悄悄改变旧来源。
- 首次收取产生 `received=true,read=false`、空剪裁/附件记录，并入队一次。重复收取返回原 instanceId，队列和数量不变。
- bottleQueue 存收到的待处理订单信实例。读信和剪词保持该实例在队列；确认后的归档/移出由 B5 处理。
- 读信命令与只读视图区分；未收到不能标已读，未读不能剪。重复读信是无副作用成功。
- 首单没有附件，不赠送特殊物品。本批保留 claimedAttachmentIds 结构与合法性检查；附件领取流程不在此批实现。
- 普通接收拒绝 `direct_followup`。直接后续投影只能进 directArchive，使用 orderId/transactionId；重复同事务不加记录，冲突事务明确报错。

**出现条件交接：** B0 将可用信件筛选归 Narrative.FindAvailable。B2 单测由场景明确给出可收信 ID，测试适配器可以按当前 dayMin/dayMax 产生输入，但必须标记为适配器；正式调度在 B4 接真实 Narrative，不将“第一天硬塞 letter_pa_01”写进 main/Letter。afterLetter/minDelivered/worldState 等条件须交真实筛选器处理，不能忽略后让信件提前出现。

出口：PlanReceive/PlanMarkRead 输入不变，状态与视图一致；未知 ID、非法状态和直接回信不能进入普通收到路径。

### P3：实现来源词条、引用与消耗候选

状态沿用 `{byId}`，条目为 `{wordId,sourceLetterInstanceId,sourceSpanId,sourceNpcId,available,consumedByOrderId}`。

- 从 Letter 的合法剪裁候选导出 source；UI 只传 instanceId/spanId，不能自报 wordId 或 NPC 来生成词。
- tokenId 按“来源实例＋来源位置”确定性生成，使用长度前缀等无歧义编码并校验冲突；重复该来源返回同一 tokenId。不同信或不同位置的同一个词是不同实例。
- 新 token 明确 `available=true,consumedByOrderId=false`，false 不可省略。定义、效果、类别、reusable 从当前相容 Data 读取，库存视图包含来源信与位置。
- 解析配方时检查所有 tokenId 存在且可用，同一实例不能同时占主/辅助槽；词条是否跨单复用与同定义副本能否同时投放是两条规则。后一规则和槽数由 B3 的配置/Order/Potion 校验，不能因为 reusable=true 放开重复实例。
- `PlanConsumption` 对 reusable=true 保持实例可用；对 false 生成 `available=false,consumedByOrderId=本单ID`。未确认的试做和预览不修改正式词条；已耗实例不删除来源记录。
- 当前正式词均 reusable=true，false 分支使用明确技术夹具，不修改 data 来凑覆盖。缺少时间 profile 的词仍可以剪和显示，作为主词的时间换算错误由 B3 拦截。

出口：六个剪词候选产生六个来源实例；重复请求无复制；来源可追溯；配方引用与消耗计算不改变正式库存。

### P4：补真实恢复器与跨块校验

- Letter/WordToken 的 ValidateSnapshot 检查字段、配置引用、布尔、稠密队列/集合及版本相容性；Restore 仅在全部校验成功时安装副本，不发接收、剪词或奖励事件。
- 跨块联合校验确认：token 的信件收到且已读、sender 相同、span 存在且对应同一 wordId、cutSpans 为 true；同一个来源位置只对应一个 token，已剪位置不能没有来源实例。
- 失效/未知位置或未知词不猜修复，不重新按新版正文编号。contentVersion 不相容保留原档，返回明确错误。
- GetSnapshot/Restore 返回值/GetView/GetInventory 修改后均不能反向改内部表；校验失败保留之前状态。
- 向 GameState 提供真实 letters/wordTokens 恢复器；尚未实现的其余恢复器仍报告缺失。

出口：剪过的缺口、已读/收到、队列、token 来源和可用性能通过真实模块公开恢复接口往返，坏快照不能部分安装。

### P5：统一命令，一次保存后再安装

在 GameState 的完整 v2 路径实现上面的三个命令及共用候选提交步骤。现有 `Save()` 仅保存当前快照，不能把它当成已经支持候选提交。

1. 检查配置、读档/不确定提交门禁、完整 v2 和真实恢复器；targetSchema=1 或缺恢复器时返回结构化错误，不开始业务变更。首次收信还须通过真实可用信筛选与 GameFlow 的打捞许可；每日数量/重置规则按既有配置与流程接入，不在 B2 新定限额。
2. 根据完整当前快照计算候选。CutWord 在同一候选里结合 Letter.PlanMarkCut 与 WordToken.PlanCut；不能靠 WordCut 监听器再生成一次词条。
3. 重复收取/已读/剪同位置返回原结果，不写盘、不增加 revision、不重复通知。合法首次变更只增加一次 revision；不分配订单或提前创建基准。
4. brewing 的基准已经保存、pending 等状态下，拒绝会改变基准的收信/已读/剪词操作；纯查看仍可用。返回具体禁用原因，不能绕过后来 B5 的门禁。
5. 校验全部候选，再用 SaveSystem 一次保存完整 Envelope。失败不安装、不留缺口、不送 token、不广播成功事件；不确定提交沿用锁定与重新 Load 对账。
6. 保存成功后同步安装全部模块再通知；防止安装期间嵌套命令。若安装异常，锁定操作并从已提交文件恢复，不把已经落盘成功谎报成可直接重试的普通写入失败。
7. 成功阅读通知 LetterRead；成功剪裁通知 WordCut/WordStored，各一次，带来源和 revision 副本；恢复档只通知 SaveLoaded。业务监听者只刷新/观察，不再结算。

**本批运行边界：** 联调测试可以使用完整、明确标记的技术 Envelope，Letter/WordToken/Economy 使用真实模块，其他恢复器只在 debug 夹具中替换。生产 main 不添加假恢复器，不新增信件专用文件，不在 v1 内偷偷追加库存字段。待 B2～B4 与 Order 恢复器齐备后，由集成人统一启用真实 v2，沿用 B1 的旧档迁移限制。

出口：成功时缺口与 token 一起出现；保存/校验失败两边都不变；同一剪裁保存成功后、通知前中断，重新读档只恢复一个词条。

### P6：整理证据和下一批接口

- 使用专用 `b2_*` 槽、独立临时目录；任何测试快捷键先绑定测试槽，沿用 R2 的隔离要求，不能写玩家默认槽。
- 运行 B2 模块与联合回归，再检查原 B1/R2 没有回退；修改 Lua 后运行当前 LSP，记录实际 Error/Warning。
- 真实引擎 File 和窗口证据单列。预览已停止时按项目规则处理，不能为检查自动复活；NanoVG 无头白图不作视觉验收。
- 在能够保留 savedata 的运行环境补真实退出/重进；当前 Maker 临时目录的限制继续挂在 V13/A10，不能在 B2 记录里勾掉。
- 交付实际接口、输入输出样例、错误码、通过/失败/待验证表与未完成依赖。此时 B3 使用 ResolveRecipe，B4 提供真实可用信调度，B5 接单及确认事务。
