# 新稿阅读与收取变体：程序交接契约

> 2026-10-03；状态：程序侧候选方案，待内容侧共同确认后实施。依据[本机计划 P4/P6](本机实施计划_新内容联调与B6_2026-10-03.md)、[文风基准](../docs/文案/文风基准与润色计划_v01.md)及 [N02 定稿](../docs/文案/普通订单/N02_两个人的晚饭_来信定稿_v01.md)。本文没有新增运行字段，没有把旧 T3 变体接入新 N02，也不决定剪词、药效、门槛或剧情。

## 1. 当前接口与缺口

| 职责 | 当前实际接口／字段 | 增量需要解决的事 |
|---|---|---|
| Letter | `ParseDefinition(letterId)` 把 `body` 的 `{{字面}}` 解析为 `segments/spans`，剪词位置为 `body:1` 等序号 | 强调独立解析；实例读取必须固定到收到时的正文版本，不能每次改读最新配置 |
| Letter | `PlanReceive(snapshot, letterId)` 返回 `{state, instanceId, changed}`；实例只保存身份、已读、缺口、附件 | 变体选择需由协调器传入已验证的只读解析结果；重复收取保留原实例 |
| Letter／WordToken | `ResolveSource(snapshot, instanceId, spanId)` 推导词定义和寄信人；`PlanCut` 生成卡 | 来源必须改从已存实例的剪词映射解析；仍不接受 UI 自报 wordId／NPC |
| Narrative | `FindAvailable(live, conditions)` 当前只支持 appearCondition.dayMin/dayMax | 信件可出现与正文选变体是两件事；不能把新条件混进旧字段后声称已支持 |
| GameState | `ReceiveLetter({letterId})`：准备候选→验证整档→保存→安装→EventBus 通知 | 在同一次候选构建内选择正文、存入实例；失败不得发 LetterReceived |
| SaveSchema／OrderAudit | schema 2 严格拒绝未知字段，检查缺口与词卡双向来源，并核验订单事务 | 新实例结构将涉及 live、baseline、candidateLive 及确认历史重放；必须独立安排版本升级 |
| PlayView | `selfIntro`、拼接的正文、`寄往：address`，暂无署名与强调渲染 | 新视图三段展示；旧运行版不伪装成已接新稿 |

复用 `Result={ok,value}`／`{ok=false,error={code,path,message,details?}}` 和纯副本约定；公共命令保持现有参数，不向 UI 暴露内部写入口。

## 2. 三段文本与强调的候选配置

建议沿用 `selfIntro`、`body`、`address`，为审定稿增加显式 `signature` 和独立的 `emphasis` 数组。`address` 只存纯地址；署名不拼进地址或自介。直回信仍由现有事实模板生成且不可剪，是否统一三段结构由内容侧另交，不能强制套入。

候选强调项：`{id, field="body", from, to, quote}`。

- `from/to` 为去掉 `{{`、`}}` 后、尚未剪裁的正文中的 UTF-8 **码点**位置，从 1 起、两端包含；不是字节、屏幕坐标或渲染行号。保留原始换行，不在解析时自动裁空白、改标点或做 Unicode 归一化。
- `quote` 必须与该范围文本完全一致，用来发现中文错位；`id` 在该正文版本中唯一。内容工具可以从审定句自动生成范围，但重复句必须指定位置，不能默认第一处。
- 初版只接受正文强调；自介／署名强调如有需要须明确交接。空范围、越界、非法 UTF-8、相互重叠的强调范围、重复 id 均报配置错误，不静默修补。
- 强调只表示加粗，不提供剪词、属性或 requirement 条件。Markdown 的 `**` 不作为控制标记进入运行正文，内容侧交接为纯文本及强调数组。
- 剪词仍以审定的 `{{字面}}` 交付，解析时产生自己的 `spanId/wordId` 和码点范围。强调可包含剪词，也可与剪词部分重叠；不能为了加粗改变 spanId、分裂一张词卡或扩大可剪范围。
- 视图在强调边界与剪词边界切分文本样式；剪下后按原剪词范围替换成一个完整缺口，不露出缺口内原字、不把剩余强调向后错移。缺口用统一缺口样式；其余正文按原码点范围保留强调。缺口表现属于本候选渲染方案，须窗口检查。
- `segments` 可新增只读样式信息，但 `spans` 仍保存独立剪词身份；一个词跨几个样式段，也只能显示一个剪词操作、产生一张卡。

N02 已批准的两句只用作强调准确性检查，不从它们推导具体订单要求；全文、剪词和要求尚未一起落 data，不在本轮写入生产配置。

## 3. 收取时选变体的候选接口

建议新增独立纯接口 `Narrative.ResolveIncoming(letterId, context)`，不要改造直接后续的 `ResolveDirect` 来承担来信。以下名称、字段是待确认方案，不是当前可调用 API。

`context` 由 GameState 从当前已验证的正式状态构造，含 `day`、`revision`、`world`、`confirmedOrders`；只读副本。不传 pending、baseline 或 candidateLive，也不接受 UI 的选择结果。

候选内容组织：每个具备变体的信定义有一个默认 `variantId` 和稠密的 `variants` 数组；每项为完整的三段正文／强调／剪词定义，配 `id`、`priority`、`when`、`unless`。首批变体只影响阅读文本与剪词来源；若要改变要求、报酬、附件或出现时间，另行交接，不能暗中随正文切换。

选择规则建议：

1. 收取前确认当前信可出现且门禁允许；只在首次收取的候选里求值一次。重复收取直接返回已有实例，不按新世界重选。
2. 非默认项 `when` 全满足且 `unless` 没有任一满足才入选，沿用现有条件语义；所有配置先校验，不能用默认项遮盖坏分支。
3. 多项命中按配置中的优先级取最高项；同优先级同时命中返回冲突，不依数组顺序猜。无命中取唯一显式默认项；缺默认／默认引用未知项拒绝。
4. 条件只读取正式世界字段或已确认订单的事实。复用已冻结的标量比较运算 `eq/ne/gte/lte`；事实需明确来源信／已确认事务，不能把不同订单的同名 factId 合并后误判。
5. 前置订单未确认是正常未满足，不是配置缺失。未知信件／规则／事实／世界字段或类型错误是配置错误，不能当成条件为 false。具体条件字段白名单与“前置订单不存在”的表达方式须在内容交接中共同冻结。
6. 返回 `{variantId, presentation, cutSources, selectionEvidence}` 的纯副本。选择器不收信、不保存、不改世界、不通知；Letter 只把已校验结果加入自己的候选实例。

没有 NPC 专用分支；N01→N02 只是内容配置中的首个使用案例。“旧面包句＋四处词”不约束新稿。

## 4. 保存、恢复与来源校验

建议每个新格式的来信实例增加一个 `resolved` 对象，具体存档 schema 编号留给独立实施批次：

| 候选字段 | 用途与限制 |
|---|---|
| `variantId` | 已选正文的配置身份；普通无变体来信也需要明确的单一版本身份，名称由交接统一 |
| `presentation` | 收取时的 selfIntro、body、signature、address、emphasis 纯数据；正文保留审定剪词标记，UI 不直接渲染控制符 |
| `cutSources` | 每个 spanId 的 wordId、原文和码点范围；与保存正文重新解析结果逐项相等；不存库存数量或药效权重 |
| `selectionEvidence` | 收取日／收取前 revision、当时已确认事务 ID 集合、选中条件的实际输入及来源；用于核对选择依据，不能引用未来确认或 pending |

这些字段需和现有 Envelope 的 contentVersion 一起核验。保存完整正文可防重新打开时重选，**不代表自动允许旧内容版本迁移**：未知版本、变体、坏词源或篡改正文仍拒绝并保留文件。

恢复须核对：

1. 实例身份／senderId 对应声明；变体属于本信；保存正文、强调及 cutSources 与该内容版本的变体一致。不能只信存档自带文本，也不能只保存变体 ID 然后每次临时拼正文。
2. 依据中每个已确认事务都存在且通过 OrderAudit；条件输入与其事实／可重建的收取时正式世界一致，收取后的事务不得反过来改变选项。需在实现时定义并验证收取前 revision 与确认顺序关系，不能仅靠自报时间声称来源可靠。
3. `ResolveSource` 对收到的实例使用其固定正文映射；wordId、sourceLetterInstanceId、sourceSpanId、sourceNpcId 仍由系统推导。
4. 已剪位置必须有对应卡实例，卡实例必须来自已读信的已剪位置；已消耗卡仍保留来源。tokenId 和同名多实例语义不变。
5. live、首次投料基准、pending.candidateLive、已确认历史引用均按同一种新格式校验。重复确认、重置和读档不能隐式重选或生成第二张卡。
6. 新字段需要 schema 变更评估；不把字段塞进当前 schema 2 并放宽未知字段检查。旧档迁移与兼容策略须单独确认并测试；未实现迁移时明确拒绝并保留原文件。

收取的原子顺序继续为：读正式状态→选择／解析→形成候选→整档校验→保存成功→安装→EventBus。保存失败不安装、不发通知；保存结果不确定沿用同槽恢复对账，不能再次选择另一正文顶替已提交结果。

## 5. 错误与验收样例

错误优先沿用 `CONFIG_INVALID`、`UNKNOWN_ID`、`SOURCE_INVALID`、`STATE_INVALID`、既有版本／保存错误，附精确字段路径；变体选择冲突的错误码在实施时统一。不吞异常默认成功。

| 用例 | 预期 |
|---|---|
| 中文、换行、重复强调句，词卡被强调完整包含或部分覆盖 | 强调定位准确；一个 span 只剪一次；缺口完整，周围强调不漂移 |
| 强调 quote 与位置不符／嵌套剪词／同一词不同位置 | 前两者拒绝；后者按不同 spanId 得到不同来源卡，不合并 |
| 已确认前置结果→收目标信 | 按正式事实选择一次，保存正文与依据 |
| 前置 pending 或重置→收目标信 | 门禁按现有规则拒绝；解除门禁后不读取未确认事实 |
| 先收目标信→以后确认前置结果 | 原实例正文、变体和剪词身份不变 |
| 多分支命中／同优先级冲突／无命中 | 按优先级／明确报冲突／唯一默认，分别验证 |
| 收取保存失败、结果不确定后同槽恢复 | 失败不通知；恢复已提交实例或保留错误，不能重复发信或重选 |
| 重开信、重启进程、重置／确认其他订单 | 已收正文不变，来源双向校验继续成立 |
| 存档未知变体、伪造确认依据、坏 cutSources、旧内容版本 | 明确拒绝并保留文件；不补空值或悄悄重算 |
| 新稿要求尚未交付 | 不从强调句生成要求，不宣布新稿可玩 |

先用隔离技术文本验证通用逻辑，再接正式新稿与真实窗口；技术用例不能替代队友剧情交付或实机验收。
