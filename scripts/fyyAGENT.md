# fyyAGENT —《寄往人间》队友开发规则

适用对象：负责程序与 UI 的队友，以及协助该队友开发的 AI 助手。

主要开发目录是 `scripts/`。本文件汇总协作边界并指向原始规范；给 AI 下达任务时，应显式要求先阅读本文件。项目的具体约定优先于通用示例，本文件不改变既定分工、配置格式或验收标准。

## 1. 可以修改的范围

以下路径均相对 `scripts/`：

| 路径 | 你的职责 |
|---|---|
| `main.lua` | 入口、初始化与系统装配 |
| `core/` | 事件总线、存档、天数与游戏流程、通用工具 |
| `systems/` | 信件、词条、炼药、订单、世界状态、剧情等玩法逻辑 |
| `ui/` | 游戏界面、交互和布局 |
| `meta/` | 存档点、回溯、成就、结局记录 |
| `debug/` | 调试面板、自检与诊断 |

**`scripts/data/` 是内容分工的例外。** 它虽然位于开发目录内，其中的人物、信件、词条、材料、设备、合成数值等配置仍归文案负责：可以读取，不自行修改。`docs/` 也由文案与设计负责人维护。

- 系统负责执行配置，文案负责内容与平衡数值；剧情、人物和订单结果不能写死在系统代码里。
- 阶段 0 配置样板已冻结；阶段 1 新增的属性条件、事实、模板、评分与待确认结构先按 [双人计划 B0](后端闭环与双人并行开发计划.md) 对齐字段和样板，再由内容负责人落盘。不用硬编码补齐缺失内容。
- `urhox-libs/` 是引擎库的只读参考副本，修改它不会影响实际运行。引擎资料、示例和模板用于查阅。
- 工作区中已有的他人改动应保留，不覆盖、不为清理工作区而丢弃。

依据：[队友上手指南：代码与内容的边界](../docs/协作/寄往人间_队友上手指南.md)、[scripts 目录职责](README.md)。

2026-10-02 用户明确授权同步相关设计文档，故本轮更新了 `docs/`；该次文档授权不改变日常目录负责人，也不授权程序代写运行内容配置。

## 2. 动手前的阅读顺序

1. [队友上手指南](../docs/协作/寄往人间_队友上手指南.md)：分工、环境与已知坑。
2. [开发计划与验收标准](../docs/寄往人间_开发计划与验收标准.md)：本阶段交付物、验收项和范围取舍。
3. [工程 AGENTS.md](../AGENTS.md)：Maker 工作流与引擎规范；根目录 `CLAUDE.md` 引用同一文件。
4. [Lua 开发指南](../engine-docs/lua-scripting-guide.md)：开发前完整阅读，遇到错误再查对应章节。
5. 从 [API 示例索引](../examples/api-index.md) 选择并阅读 3 个相关示例，同时满足项目与引擎指南的阅读要求。

本项目的界面开发可从 UI 组件画廊、拖拽背包、富文本聊天三个示例开始。涉及具体功能时，再读对应的引擎 recipe 和类型声明。

引擎 API 以 Maker 项目本地资料、LSP 类型声明及相关示例为依据；不要凭记忆编写接口，也不要假设它与标准 Urho3D 完全一致。

## 3. 实现时的硬约束

### 结构与通信

- 沿用当前基于 `templates/scaffold-2d.lua` 的入口和 `Start()`／`Stop()` 生命周期，在既有骨架上增量开发。
- 跨模块通信走 `core/EventBus`，各模块维护自己的状态，不直接读写其他模块的内部数据。
- 模块协作可通过约定的公共接口请求计算或读取副本，跨模块通知仍走 EventBus。双人写代码前先读 [并行分工](后端闭环与双人并行开发计划.md#4-两个人如何并行)，一文件一主改人，入口、存档版本与总自检由一人集成。
- 按现有目录职责拆分代码；单文件超过 1500 行必须拆分。
- 自有模块路径相对 `scripts/`，例如 `require "systems.Potion"`；资源路径相对 `assets/`，例如 `Textures/letter.png`，不加 `assets/` 前缀。

### UI 与 Lua

- 目标为 TapTap 移动端；用户于2026-10-10暂时改定横屏，先做主页总体候选图。开始布局或手机交付前，先读[方向口径 r2 与核查](../docs/验证/2026-10-10-maker-screen-orientation.md)。旧 **1080×1920** 画布与现有代码保留，不因创意试稿自动改版；自适应布局与 `SafeAreaView` 按实际窗口验收。
- UI 使用 `urhox-libs/UI`，遵守 [UI 系统文档](../engine-docs/recipes/ui.md)；文字、按钮、菜单等使用 UI 控件。
- **`UI.Init` 必须显式指定 `Fonts/MiSans-Regular.ttf`**，参考 `main.lua` 的现有写法。默认 NotoSansSC 在本项目运行时缺失，会导致整个 UI 不渲染。
- Lua 版本为 5.4；中文直接写中文字符，不使用 JSON 风格的 `\uXXXX` 转义。
- 空值变量和控件引用应有准确类型标注；`FindById` 返回的通用控件需确认具体类型和非空，再调用子类方法。
- 输入判断使用引擎枚举，不猜按键或鼠标按钮的数字值。存档使用引擎 `File` API 与相对路径，具体用法查 [文件存储文档](../engine-docs/recipes/file-storage.md)。

### 玩法与配置

- 魔药严格按照 [synthesis.lua](data/synthesis.lua) 注释规定的 **八步求值顺序**实现，数值读取配置，不另写配方查找表或自行改变算法。
- 槽位上限读取 [equipment.lua](data/equipment.lua) 的 `slots`。基础容量：**主词条 1、辅助词条 2、原料 2、特殊物品 1**；满槽必须限制继续投料。
- `Order` 判断字面条件、根据已解析事实与人物认知配置评分，并协调本单基准、待确认、确认 / 重置；人物后果由 WorldState/Narrative 在副本中计算。成功保存整份结果后才提交并通知，重复确认不得重复扣料、发奖或叠加药效。
- 玩家始终留在魔药铺，人间信息通过信件、附件和药效引发的后续抵达。当前计划不增加外出探索、主动调查、联机、战斗或复杂装修。

## 4. 当前接手目标：阶段 1 核心闭环

实现：**打捞 → 读信 → 剪词 → 炼药 → 字面判定与发货 → 直接后续与评分 → 确认 / 重置 → 正式世界变化与延迟来信**。

- 系统：`Letter`、`WordToken`、`Potion`、`Order`、`WorldState`、`Narrative`。
- 支撑：修复实际存档恢复，接入 Economy 的最小库存/货币账本；完整经济与商店仍在后续阶段。
- 界面：打捞、读信与剪词、炼药，并串起词条库存、结果展示与发货。
- 内容接入规模：1 个 NPC、2 封逻辑信件（首信与含多个版本的直接后续）、5～8 个可剪词、3～5 种材料；内容配置由文案提供。
- 同一主词条搭配不同辅料，至少产生 3 种可区分结果，以 A13 为准。
- 此阶段不做商店、档案桌、身份与案件；后续按开发计划逐阶段推进。

当前已接受规则和调试初值先读 [开发讨论结论](开发讨论结论_2026-10-02.md)，实施顺序按 [后端闭环与双人并行开发计划](后端闭环与双人并行开发计划.md)：先一单逻辑，再简单可操作界面，最后正式美术。初值写入文档不代表已经配置、实现或通过运行验收。

设计草案与实施计划有差异时，依照当前阶段的明确验收条款执行。范围取舍遵循开发计划 §1.6，不自行降低验收标准或削减规定的内容密度；提出新功能时同步说明开发成本和排期影响。

## 5. 验证与完成标准

1. 修改 Lua 后运行可用的 LSP 诊断，**构建前确保没有 Error**。
2. 使用本地预览检查启动日志、布局和实际操作。运行命令必须明确指向当前工程的绝对路径。
3. 纯 UI 项目不能用无头截图作视觉验收；`Widget:GetComputedSize()` 可用于布局检查，实际显示与操作需查看窗口，最终以手机实机为准。
4. 阶段 1 按开发计划 **A1～A19** 逐项走查，保留实际结果；纯逻辑通过不代表 UI、保存失败、退出重进或实机操作已经通过。

特别检查：剪词后空缺保留、词条来源可查、订单失败原因明确、后续信体现发货因果、重启恢复全部关键状态、连续操作无报错或布局异常。A12／A13 的新增信件和词条测试，由文案配合修改配置，验证系统代码无需跟着修改。

仅文档变更时，检查文字、链接与变更范围即可，不因此触发游戏预览或远端构建。

## 6. Git、Maker 与交付边界

- 开工和提交前核对当前分支、工作区差异及 `git remote -v`。本轮协作使用 `fengyycon`。
- 约定的远端用途是：`github` 指向 GitHub，`origin` 指向 Maker。以本机实际配置为准，不能仅凭名称推送。
- 日常 GitHub 推送与 Maker 提交构建分开处理。Maker 构建按工程 `AGENTS.md` 的 `maker_build_current_directory` 流程执行。
- 组长于 2026-10-03 确认：以后只说“提交”“推送”或“提交推送”时，默认同步 Maker 和 GitHub；明确只要一端时按当次要求执行。先由 Maker 官方流程提交、推送并构建，再用 `git push github main` 将同一提交同步到已核对的 GitHub 仓库。分别验证两端结果；任一端失败时说明具体状态，不能只完成一端就报告全部完成。
- 本地检查和预览不等于授权提交、推送或远端构建；按明确的交付请求执行相应操作。
- **不新建 Maker 项目，不重跑 `taptap-maker init`**，以免改写 GitHub 远端。
- 遵守 `.gitignore`；不强制提交引擎资料、本地绑定、缓存或构建产物。凭证不写入代码、聊天或提交内容。
- 本地开发无需先取得云端 token；远端构建前再确认账号授权及既有 Maker 项目权限。
- 当前应用已有方向登记，二维码沿用该值，不能套用首次缺失方向时的选择流程。仅在用户明确要求手机二维码/扫码测试时按当前 Maker 工具执行；现有应用的方向纠正路径先按核查报告确认，不自行改本地字段、新建或换绑应用。

## 7. 给 AI 助手的附加要求

- 先说明本轮范围，执行后区分已实现、已验证、失败与未验证，不把分析任务自动扩展为修改任务。
- 相关代码修改后检查预览状态；若窗口正在运行，按 Maker 规范刷新并读取新日志。已停止的会话不因修改代码而擅自重新启动。
- 遵守当前会话的个人项目汇报规则；主动汇报属于 AI 助手的责任，不要求队友额外填写固定模板。
- 遇到规则冲突，说明具体来源和冲突点，按当前明确授权与项目具体约定处理，不暗中改写分工或验收标准。
