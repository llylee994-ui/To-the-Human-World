## 1. 先做什么

先打通埃利亚斯·沃德的一整单游戏逻辑，再接简单可操作界面，最后把已经认可的美术主页和其他正式界面接上去。这里的“后端”指玩家设备里的 Lua 游戏逻辑，当前不新增服务器、HTTP 接口或云存档。

阶段 1 仍只做 1 个 NPC、2 封逻辑信件、词条、原料与确认/重置。旅行票、家居、案件和身份参数先完成内容配置准备，按原阶段推进实现。

```mermaid
flowchart LR
    A[字段与模块交接约定] --> B[无正式美术的逻辑闭环]
    B --> C[简单按钮和文字的可玩界面]
    C --> D[正式美术与交互]
    D --> E[A1至A19逐项验收]
    A --> F[内容配置和后续文案]
    F --> B
```

程序测试和临时界面都使用同一套游戏逻辑。临时按钮只是输入入口，不能另写一套“演示用发货/扣库存”，也不能把规则藏进按钮回调。正式 UI 接管显示和操作后，后端保持同一行为。

先做后端不等于把全部阶段 1～3 写完才第一次点界面。第一单逻辑通过后，必须尽快用简单界面验证剪词、投料、后续和重置是否顺手；正式美术可以后接。

## 2. 开工前共同约定的输入输出

本节是需要冻结的交接内容，不宣称相应函数或文件已经存在。字段名称和类型由开发提出、内容方据此填写；配置样板通过校验后锁定版本。任何改名先通知另一方并一起更新样板与调用方。

| 对象/边界 | 必须写清的内容 |
|---|---|
| 信件与词条来源 | 信件 ID、词条定义 ID、来源信件/裁剪位置、是否已剪、是否可复用；同一位置只能获得一次 |
| 投料请求 | 本单 ID、设备 ID、主词与辅助词引用、原料及份数、特殊物品引用；检查槽位、来源、库存与重复投放规则 |
| 药效结果 | 标签及权重、强度分级、持续时间与单位、生效延迟、稳定性提示、副作用；保留必要计算依据供诊断 |
| 字面判定 | 是否允许发货，以及每条未满足条件的要求值/实际值/原因；明确未配置的条件如何报错 |
| 事件与后续 | 候选人物状态、直接事件事实、命中的片段、最终文本、星级与本人反馈；保证内容来源可追踪 |
| 本单基准与待确认对象 | 基准版本、本单唯一 ID、配方、候选完整状态、消耗/奖励、后续及评分、确认状态 |
| 保存与恢复 | 正式状态和待确认记录如何一起保存；保存失败返回什么；重启如何恢复；旧档如何迁移 |
| 界面读取 | 给 UI 的状态副本、可执行操作、禁用原因与失败提示；界面不持有可改写的系统内部表 |

跨模块通知使用现有 `core/EventBus`。Order 可以通过明确的公共接口请求计算或读取副本，不直接读写其他模块内部数据。正式 `PotionDelivered` 只在成功保存并确认后通知；监听者不能再次扣料、发奖或叠加药效。

## 3. 按可验证结果拆分工作

以下 B0～B7 是阶段 1 内部的实施批次，不是原开发计划中阶段 0 的 B1～B7 验收项，也不替换阶段 1 的 A1～A19。

| 批次 | 要完成的事 | 主要文件位置（相对 scripts） | 出口条件 |
|---|---|---|---|
| B0 交接基准 | 完成本节输入输出、字段样板、单位、错误处理；内容方提供首单数据包 | 文档约定；`data/` 由内容方落盘 | 两人用同一份输入，可以明确说出期望输出；缺配置项被点名，不能默认通过 |
| B1 存档与最小账本 | 核对并修复启动/调试读档、false 值恢复；保存正式进度和待确认记录；接最小材料/货币账本 | `main.lua`、`core/SaveSystem.lua`、`core/GameFlow.lua`、`systems/Economy.lua` 的阶段 1 最小部分 | 新开、读旧档、读损坏档、恢复待确认可区分；重启不丢本单状态；无永久重复发奖 |
| B2 信件与词条 | 出现条件、领取、已读、裁剪位置、来源词条与复用策略 | `systems/Letter.lua`、`systems/WordToken.lua` | 首信只领取一次；同一位置只剪一次；重新打开/读档后缺口与库存一致 |
| B3 炼药与判定 | 槽位/库存检查、八步求值、时长等属性、字面条件与失败原因 | `systems/Potion.lua`、`systems/Order.lua` 判定部分 | A～D 和超时/标签不足用例可重复计算；超槽、无库存、未知配置明确拒绝 |
| B4 后果与后续 | 副本上的人物变化、事实判定、片段匹配、组合覆盖、互斥与兜底 | `systems/WorldState.lua`、`systems/Narrative.lua`；Order 评分部分 | A～D 有可解释差异；D 不混入完整回忆片段；无占位符、矛盾文本或凭空证据 |
| B5 完整本单流程 | 基准→试做→后续→确认/重置；接存档失败、退出和重复操作 | `systems/Order.lua` 协调，配合各模块公共接口 | 重置回基准；重复确认只提交一次；保存失败不改正式状态；读档恢复同一结果 |
| B6 简单界面联调 | 用文字和普通按钮完成打捞、读信剪词、投料、查看结果、后续确认/重置 | `debug/` 临时入口或 `ui/` 简单界面；`main.lua` 统一装配 | 人不用调试命令也能完整操作一单；后端错误和禁用原因能显示出来 |
| B7 正式页面与验收 | 按已认可美术样稿接主页、信件、炼药、抽屉与状态反馈 | `ui/`、`ui/components/` | 完成 A1～A19 实机走查，含中文、移动端触控、长信滚动和连续操作 |

B1 中的 Economy 只承担阶段 1 必需的库存、候选消耗与确认结算，不实现商店、商品解锁、完整经济或家居。沿用既有 Economy 职责，避免在 Order 和 UI 各自维护一份材料数量；阶段 2 在这份最小账本上扩展。

B1 与 B3 的独立计算部分可在 B0 后并行；B2 与 B4 可按已冻结样板分别推进。B5 依赖它们联调通过。依赖方尚未完成时，测试可用明确标记的固定夹具验证本模块，联调与验收必须换成真实模块和内容配置。

B1 已复现并修复入口层级、false 与调试读取三项问题，并接入可靠保存协议、统一恢复及最小账本。R2 的测试槽绑定遗漏也已修复。实际结果与限制见 [B1 实施](actions/2026-10-02-b1-implementation.md)、[C1 接入](actions/2026-10-02-b1-content-integration.md) 和 [R2 修复](actions/2026-10-02-b1-content-review.md)。阶段 0 的 12 项自检不能代替完整新状态的运行验收。

## 4. 两个人如何并行

### 模式一：现有的一名开发＋一名文案，推荐默认采用

| 人员 | 负责范围 | 可以同时推进的工作 |
|---|---|---|
| 开发 | `scripts/` 程序，排除内容目录；负责 main/core/systems/debug/ui | 实现上表 B1～B5，制作计算与流程检查，准备 B6 接入 |
| 文案/设计 | `scripts/data/` 内容与校验入口、`docs/` 设计内容 | 补首单配置和 A～D 后续、评分；准备阶段 3 订单投放/经济表、词库、成对瓶子与结局稿 |

开发提供字段含义、正常/失败样例和校验要求，文案按样板填写。文案能继续扩充人物与片段，开发不必等全部故事写完；依赖缺失字段的功能不能用硬编码剧情补齐。

### 模式二：如果两个人都承担 Lua 开发，可按文件拆成两组

这是可选分工建议，不自动改变现有内容负责人，也不认为询问并行就已分派给另一位同伴。

| 负责人 | 独占的主要模块 | 对外交付 |
|---|---|---|
| 开发 A：流程与状态集成 | `Letter.lua`、`WordToken.lua`、`Order.lua`、阶段 1 最小 `Economy.lua`；`main.lua`、`core/` 与调试入口 | 真实信件/库存、订单生命周期、保存恢复、正式结算与界面操作入口 |
| 开发 B：药效与剧情规则 | `Potion.lua`、`WorldState.lua`、`Narrative.lua` 及各自模块测试 | 药效结果、候选世界状态、事实与兼容后续；不直接保存正式世界或发奖励 |

Order 的字面判定与评分归 A；B 提供药效、事实和后续表达。两人共同评审配置字段，但只有内容负责人改 `scripts/data/`。如果同伴兼做开发 B 与文案，这两部分占用同一个人的工时，不能按两条独立产能计算。

### 共同的协作规则

1. 同一任务批次，一个文件只有一个主改人。`main.lua`、`core/`、整体存档版本和总自检入口由集成人统一改。
2. 两名开发使用独立工作目录/检出处理代码，避免同一文件夹内切换分支影响对方运行。当前 `fengyycon` 保留；新分支和工作区在实际分工落定时按仓库约定处理，本轮不创建。
3. 先锁输入输出与事件含义，再分别编码；改接口时先改交接约定、样板和双方调用点。
4. 每完成一个能运行的小批次就合入联调，不等六个模块全部完成才第一次接线。集成人负责主分支同步与 Maker 预览；提交/远端构建仍按既有授权执行。
5. 测试也按模块分文件，另一人的业务文件通过公共接口使用，不自行修补对方内部状态。
6. 本单发货造成的正式变化只通过 Order 的一次确认流程提交；WorldState/Narrative 在副本上计算。事件通知不能成为第二套结算入口。剪词、跨天等其他操作仍由各自模块负责保存，遵守本单待确认期间的操作限制。

## 5. 最小验收场景

| 场景 | 要检查的结果 | 对应原验收 |
|---|---|---|
| 首信裁剪与读档 | 重复领取/重复剪同位置无新增；来源与缺口一致 | A2、A4、A5、A10 的逻辑部分 |
| 合成与约束 | 八步顺序、槽位上限、库存不足、未知词/原料、至少三种结果 | A6、A7、A13 的逻辑部分 |
| 首单正负例 | A～D；8 小时与加花瓣后的 10 小时；sleep 不达标；具体失败原因 | A7、A14 |
| 后续拼装 | 单效果、组合覆盖、互斥、通用片段、缺填充值 | A9、A15 的逻辑部分 |
| 本单重置 | 材料、词条、余额、订单、NPC、队列、计数回基准；先前剪词保留 | A8、A16、A17 |
| 重复与恢复 | 多次确认/重开后续无额外奖励；待确认退出重进一致；同输入同事实 | A10、A17、A18 |
| 保存失败 | 正式状态不变化，保留待确认；再次成功只提交一次 | A18 |
| 评分 | A/B 三星、C 二星、D 一星；同单报酬一致；重置撤销评分 | A19 |
| 内容扩展 | 内容方只改配置，新增首信和词条即可接入 | A12、A13，需现场改配置验证 |

不能靠检查返回表的形状替代状态变化、存档重启或失败注入。暂时使用模拟保存器的测试需标明，真实引擎 File 存取与重新启动仍要验证。

逻辑验收通过后，A1、A3 的显示要求，以及 A4/A5/A6/A8/A9 的操作和呈现、A11 的连续操作、中文排版等仍需在界面与实机上走查。不得把逻辑检查通过写成阶段 1 全部通过。

新增界面沿用 `UI.Init` 中的 `Fonts/MiSans-Regular.ttf`。视觉验证看窗口与布局尺寸，不用无头截图判断 NanoVG 图层。
