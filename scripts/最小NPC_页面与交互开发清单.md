## 1. 范围、依据与当前起点

本阶段交付 **3 个主页面 + 5 个浮层**。开瓶发生在主页，剪词发生在读信页，后续来信复用读信页，不另造新页面。

最小内容规模：路人甲 1 人、首信与后续信共 2 封、首信已有 6 个可剪词、4 种原料；同一个主词条必须能合成至少 3 种可区分结果。

本稿按早期 A1～A13 拆解；现行完整要求以 [开发计划与验收标准](../docs/寄往人间_开发计划与验收标准.md) 的 A1～A19 为准。协作边界见 [fyyAGENT](fyyAGENT.md) 和 [队友上手指南](../docs/寄往人间_队友上手指南.md)。页面排布与浮层明细保留供 UI 阶段参考；数据缺口的最新状态以 [讨论结论 §8](开发讨论结论_2026-10-02.md#8-仍需交付或补齐的内容) 为准，不能据旧待定项重开已确认选择。

只开发 `scripts/` 中的程序与 UI，`scripts/data/` 与 `docs/` 由文案维护。此阶段不增加商店、设备购买、档案桌、身份、案件、结局、配方书收集、外出地图或 3D 漫游。

## 2. 页面与浮层总表

| 编号 | 要做的界面 | 进入方式 | 必须显示 | 离开方式 |
|---|---|---|---|---|
| P01 | 海边主页／打捞页 | 启动、其他页面返回 | 海面和海浪、漂流瓶、打捞按钮、天数、货币、已打捞的信件列表 | 点开瓶／信件进入 P02；点炼药进入 P03 |
| P02 | 信件展开与剪词页 | P01 点“开瓶读信”或已收到的信 | 信纸、标题、寄信人、自我介绍、正文、地址、可剪词、剪后缺口、订单要求 | 返回 P01；点“为这封信炼药”进入 P03 |
| P03 | 炼药页 | P01“炼药”或 P02“为这封信炼药” | 当前订单、炼药锅、4 类槽位、材料选择、炼制按钮 | 返回进入它的页面；炼制后打开 W03 |
| W01 | 词条库存抽屉 | P01／P02／P03 点“词条” | 已获得的词条、来源信件、来源人、是否可复用 | 关闭后回原页面 |
| W02 | 投料选择抽屉 | P03 点一个空槽 | 对应该槽位的可用词条或材料、已选状态、添加按钮 | 添加成功或点取消后回 P03 |
| W03 | 魔药结果与订单判定浮层 | P03 炼制成功，或查看尚未寄出的结果 | 效果名称、强度、持续时间、其他属性、符合／不符合、缺失条件 | 调整配方回 P03；满足要求后进入 W04 |
| W04 | 发货确认浮层 | W03 点“发货” | 收件人、信件标题、该信地址、药效摘要 | 取消回 W03；确认成功回 P01 |
| W05 | 结束当天确认浮层 | P01 点“结束当天” | 当前天数、未处理信件／订单数量、跨天说明 | 取消回 P01；确认后留在 P01 并更新天数 |

正常游玩路线：

```text
P01 海边主页 → 打捞 → 待开漂流瓶 → 开瓶
    ↓
P02 展开信件 → 点击剪词 → W01 查看词条和来源
    ↓
P03 为这封信炼药 → W02 选择投料 → 炼制
    ↓
W03 查看结果和字面判定 → W04 确认发货
    ↓
P01 海边主页 → 按配置等待／跨天 → 打捞后续瓶 → P02 读后续信
```

## 3. P01：海边主页／打捞页

### 3.1 页面上要画出来的东西

- [ ] **H01 顶部状态栏**：显示“第 N 天”、中文时段、货币图标与数值。天数和时段读取 GameFlow；货币读取玩家状态，初值由 DATA03 提供。不把 `day` 这类内部枚举直接展示给玩家。
- [ ] **H02 海面背景**：屏幕主要区域能看出海面、岸边或店铺临海边缘；海面有至少两层缓慢循环的波浪运动。第一版可由代码绘制占位图形，正式画风由你决定。
- [ ] **H03 待打捞漂流瓶**：存在可打捞内容时，在海面画出普通漂流瓶并轻微上下浮动；没有时移除该瓶。未打捞前不显示信件正文和人物资料。
- [ ] **H04 打捞信息**：显示“当前可打捞：N”，N 是已经满足配置条件且尚未收到的信件数量，不显示未经配置的每日固定上限。
- [ ] **H05 打捞按钮**：海面下方固定放置“打捞”；有候选信且流程允许时可点，否则置灰，并在按钮旁显示“暂时没有漂流瓶”或“当前无法打捞”。
- [ ] **H06 已打捞列表**：显示未开瓶卡片和已开信卡片。未开瓶显示瓶子图与“开瓶读信”；已开信显示标题、寄信人以及“待处理／已寄出／后续来信”等适用状态。长列表可以滚动。
- [ ] **H07 常驻操作**：放置“词条”“炼药”“结束当天”三个入口。词条为空仍可打开库存；没有可处理订单时炼药入口置灰并显示原因。

### 3.2 按钮具体做什么

- [ ] **H08 点击打捞**：先锁住按钮，取一个当前符合条件且未收到的信件 ID，播放瓶子从海面进入待处理区的短动画，成功后插入一张未开瓶卡片；候选数量减一，再恢复按钮可用状态。
- [ ] **H09 防重复打捞**：连点、页面重开、动画中再次触摸，都不能让同一封信重复入队。游戏状态更新不依赖动画是否播放完。
- [ ] **H10 点击开瓶**：将该瓶标记为已开，打开对应 P02；首次成功展示时记录已读并发出一次已读事件，供 `afterLetter` 条件使用。之后主页显示这封信的卡片，再点卡片可以重新读信，不重复触发首次已读，也不重新发放瓶子或词条。
- [ ] **H11 点击炼药**：存在一封已打开且未完成的订单信时直接进入它的 P03；存在多封时，滚动到主页信件列表并提示“选择一封信，再点为这封信炼药”，通过 P02 明确选择目标。未开瓶不能直接炼药。
- [ ] **H12 新信提示**：后续信满足条件时，只更新海面的可打捞瓶与数量，并显示“有新的漂流瓶”；玩家仍需打捞、开瓶才能读到，不强制跳转打断操作。

**验收操作**：新游戏能看到海浪、天数、货币和打捞按钮；打捞一次产生首信的瓶；连续点击不会重复领取；开瓶后能进入读信页，再返回能重开同一封信。

## 4. P02：信件展开与剪词页

### 4.1 页面上要显示的内容

- [ ] **L01 页面框架**：顶部固定“返回海边”、信件标题和寄信人；中间是可纵向滚动的信纸；底部固定词条库存入口与“为这封信炼药”按钮。固定栏不能压住正文最后一行。
- [ ] **L02 三段信文**：按“自我介绍 → 正文 → 详细地址”顺序完整显示。分别读取 `selfIntro`、`body`、`address`，保留换行和段落；三段能通过间距或小标题区分。
- [ ] **L03 信件地址**：始终使用当前信件的 `address`，不能擅自用 NPC 档案地址覆盖它；两者将来可能有意不同。
- [ ] **L04 订单要求卡**：正文外单独显示 `requirement.desc` 和当前订单状态。首信应自动显示“希望能踏踏实实睡一晚，第二天起来还有力气干活”，不在代码中复制这句话。
- [ ] **L05 可剪词表现**：把 `{{词}}` 解析成可点击片段，画出下划线／剪裁边框，并在页内提示“点击标记词语可剪下”；玩家看不到双花括号。
- [ ] **L06 首信接入检查**：累、快乐、忘记、梦、安静、睡觉六处均可见、可剪；未被标记的普通文字不能剪。
- [ ] **L07 附件区域**：当前 `attachments = {}`，整块隐藏，不放假的道具卡。带道具的附件处理暂不扩展到本切片；特殊物品槽按 P03 的禁用状态显示。

### 4.2 剪词的完整行为

- [ ] **L08 点击一个可剪词**：发起一次裁剪操作；成功后，原位置替换成可见的纸张缺口或下划线空位，库存新增一个词条实例，并短暂显示“已收下：词语”。不打开二次确认框。
- [ ] **L09 缺口占位**：缺口至少保留原词的显示宽度，不能把前后文字无痕拼起来；剪前后段落仍能正常换行和滚动。
- [ ] **L10 一处只剪一次**：每个裁剪位置由“信件 ID + 该标记的出现序号”标识。同一个词若在同一封信出现两次，是两个位置；不能仅按词的文字判断是否已剪。
- [ ] **L11 无法重复领取**：剪过的位置不可再点击领取。快速连点、关闭重开信件、重启游戏后均保持原缺口且不重复加库存。
- [ ] **L12 触摸与滚动区分**：手指上下滑动信纸时只滚动，不误剪起点经过的词；轻点词语才裁剪。词被裁剪后保留当前阅读位置。
- [ ] **L13 跳转炼药**：点“为这封信炼药”把当前信件 ID 作为目标订单交给 P03；未获得词条时允许进入并明确提示先剪主词条，不能静默失效。
- [ ] **L14 已发货／后续信**：已寄出的订单仍可阅读已有文字与缺口；“为这封信炼药”改为不可用的“已寄出”。无订单后续信不显示炼药按钮；这类信的识别规则需要 DATA05 补齐。

**验收操作**：展开首信，滚到地址，再滚回正文剪“睡觉”；库存新增该词；退出重开信件，原位置仍有缺口。剪词前后都能读完全部中文。

## 5. W01：词条库存抽屉

- [ ] **I01 打开与关闭**：从任一主页面打开覆盖式抽屉，背景页面暂停点击；点关闭后返回原位置，不丢失阅读滚动位置或炼药投料。
- [ ] **I02 空库存**：没有词时显示“还没有词条，先从信里剪下标记的词”，提供关闭按钮，不展示整个词库当作已拥有物品。
- [ ] **I03 词条卡片**：每个已获得实例显示词语、来源信件标题、寄信人，以及“可重复使用／使用后消耗”。名称读取词表，来源来自裁剪记录。
- [ ] **I04 同词不同来源**：两个来源的相同词不能合并丢失来源；列表可分别显示两个实例。已投入当前配方的实例显示“已放入”。
- [ ] **I05 持久化与刷新**：剪词成功后立即刷新，重新进入游戏仍在；配置 `reusable = true` 的词炼制后仍可用，`false` 的词只在炼制成功时消耗，不在点选时提前消耗。

**验收操作**：首次打开是空状态；剪下两个词后，两张卡片均显示正确词名和首信来源；关闭抽屉后原页面保持不变。

## 6. P03 与 W02：炼药页和投料选择

### 6.1 炼药页布局

- [ ] **B01 订单栏**：顶部显示“为谁炼药”、对应信件标题、订单要求；提供“返回信件”。从主页进入也必须能明确知道当前目标订单。
- [ ] **B02 锅与工作台**：中间显示当前设备名称、锅或炉的图形，以及炼制期间的液体／气泡动效；读 `equipment.name`，不把第二台未拥有设备显示为可用。
- [ ] **B03 主词条槽**：显示 1 格和“主词条 0/1”；投入后显示词名及移除按钮，计数变为 1/1。
- [ ] **B04 辅助词条槽**：显示 2 格和“辅助词条 N/2”；每格都能单独移除。容量实际由当前设备 `slots.auxWord` 创建，不写死两个控件。
- [ ] **B05 原料槽**：显示 2 格和“原料 N/2”，投入后显示名称。第三份原料被拒绝，并显示“原料槽已满，请先移除一份”。
- [ ] **B06 特殊物品槽**：保留 1 格布局，当前首信无附件，显示“本信无可用特殊物品”并禁用；不能当第三个原料槽使用。
- [ ] **B07 底部操作**：显示“词条”“清空投料”“炼制”。没有主词条时“炼制”置灰并显示“请放入主词条”；正在炼制时锁住投料与炼制按钮。

### 6.2 点击空槽之后的选择抽屉

- [ ] **B08 选主词条／辅助词条**：打开 W02，只列玩家已经剪到且可用的词条；每项显示词名、来源、“放入”按钮。同一词条实例已放在任一槽内时不可再次放入另一个槽。
- [ ] **B09 选原料**：打开 W02，列出海盐、夜露、灰烬草、干花瓣的名称、`desc`、属性修正和可用数量。数量来源由 DATA03 提供，不能把 `price` 当库存或自动送满无限份。
- [ ] **B10 加入与取消**：点“放入”前重新检查类型、槽位和可用数量；成功后关闭抽屉并刷新槽位计数；点取消不改变任何投料。
- [ ] **B11 移除与清空**：移除一格只撤销该格的预留；“清空投料”撤销全部预留。尚未炼制时不扣除物品，不因来回点选减少库存。
- [ ] **B12 草稿保留**：在同一运行会话中，返回信件查看要求再回炼药页，保留本订单尚未炼制的投料；不需要保存这个临时草稿到磁盘。切换目标订单时清空旧草稿，避免误投。
- [ ] **B13 原料数量边界**：基础设备最多放两份原料，每份占一槽；两份同种原料仍占两槽并校验两份库存。A6 的验收必须使用两种不同原料，不由此强制所有配方都填满原料槽。

### 6.3 炼制动作

- [ ] **B14 点击炼制**：重新校验订单、主词条、容量与材料，然后严格执行 [synthesis.lua](data/synthesis.lua) 注释的八步求值顺序；结果生成成功后才提交消耗并打开 W03。
- [ ] **B15 防重复炼制**：连续点击一次操作只生成一份结果、只扣一次消耗；动画不能承担发放和扣减状态的职责。
- [ ] **B16 不稳定提示**：按配置标记“可能炼制失败”，阶段 1 只提示，不能擅自增加随机炸锅、销毁材料或概率判定。
- [ ] **B17 未寄出结果保管**：结果绑定目标订单并保存；关闭结果浮层后，炼药页有“查看待寄魔药”入口。已有未寄出结果时先处理该结果，不因再次炼制无提示覆盖它。
- [ ] **B18 返回调整**：W03 点“调整配方”时，若已炼制并产生消耗，先明确提示丢弃该未寄出成品且不退已消耗物品；确认后清空成品并返回投料状态，取消则保留成品。

**验收操作**：放入“睡觉”作为主词条，再放两种原料；尝试第三份被拒绝；移除一份后可换另一种；点炼制得到一份结果。具体初始材料数量未补齐前，这部分只能做界面与逻辑联调，不能声称完整玩法验收通过。

## 7. W03／W04／W05：结果、发货与跨天

### 7.1 W03 魔药结果与字面判定

- [ ] **R01 药效卡**：显示药瓶、由效果标签名称组成的效果摘要、每项效果的强度等级、持续时间、生效速度、副作用和稳定性；效果名称读取 `effects.lua`，等级读取合成配置。
- [ ] **R02 时间显示**：持续时间和速度按 DATA04 确定的单位与换算显示。现阶段只有属性修正，不能把 `duration = 2` 私自解释成“两小时”或“两天”。
- [ ] **R03 判定结论**：固定显示“符合字面要求”或“不符合字面要求”。逐项比较 `requirement.tags`，标签不存在按未达到处理；不以关键词命中或配方名字代替计算。
- [ ] **R04 不符合的原因**：列出每个未达标效果的名称、要求最低值、实际值，例如“睡眠：需要 ≥0.8，当前 0”；数值读取本订单与结果，不只显示“失败”。
- [ ] **R05 发货按钮状态**：符合要求且订单未完成时“发货”可点；不符合或已经寄出时置灰并显示原因。“调整配方”始终能回到可继续处理的状态。
- [ ] **R06 判定边界**：副作用和不稳定提示不额外否决一份已经达到字面标签条件的魔药；订单系统不替玩家作安全或道德评价。

### 7.2 W04 发货确认

- [ ] **S01 确认信息**：显示收件人、信件标题、当前信件地址和该成品药效摘要；提供“返回检查”“确认寄出”，不允许手填一个与信件无关的地址。
- [ ] **S02 再次校验**：点确认时重新检查订单未发货、成品存在且符合要求；通过后锁住按钮，记录订单完成，标记成品已寄出，累计发货次数加一，并发出发货事件。
- [ ] **S03 后果与存档**：WorldState 按 DATA01 的配置规则更新人物状态，Narrative 根据新状态检查解锁条件；把订单、人物状态、后续信解锁记录作为一致状态保存，然后返回主页并显示“已寄出”。
- [ ] **S04 防重复发货**：连点、浮层重开、游戏重启不能给同一订单再次发货、再次改变人物状态或再次解锁同一封后续信。
- [ ] **S05 不提前剧透**：发货成功反馈只展示寄送结果；具体人间后果通过后续信体现。开发期可在调试面板查看状态变化。

### 7.3 W05 结束当天

- [ ] **DAY01 跨天说明**：列出还未开瓶、还未寄出的数量，提示“未处理的信件和待寄魔药会保留”；提供“继续处理”“结束并进入下一天”。
- [ ] **DAY02 推进一天**：确认只调用一次正常日切流程，更新天数、重算可出现信件、保存状态并关闭浮层；不要求玩家用 Z 键或调试按钮才能收到后续信。
- [ ] **DAY03 跨天不代办**：不自动剪词、不自动炼药、不自动发货；本切片不新增订单过期惩罚。未收到信件的 `dayMax` 仍参与出现条件判断，不能忽略。
- [ ] **DAY04 后续来信复用**：第二封信满足配置条件后进入主页可打捞候选；玩家打捞开瓶后，P02 显示它自己的标题、三段文字和已有裁剪标记，能读出与第一次发货的因果关系。

**验收操作**：做一份不满足睡眠要求的结果，确认提示具体缺项且无法寄出；再做满足要求的结果寄出，调试面板出现人物状态变化；按内容规定跨天，打捞并读到后续信。不能用调试按钮手动塞入后续信代替此验收。

## 8. 页面背后必须接好的程序任务

这些任务没有独立游戏页面，但缺少任意关键项，页面就只是展示样板。

### 8.1 配置自动接入

- [ ] **C01 统一读取**：复用 [Data.Load 与查询入口](data/content.lua)，按 ID 关联信件、寄信人、词条、原料与设备。渲染代码中不出现仅服务 `letter_pa_01` 或 `npc_passerby_a` 的条件分支。
- [ ] **C02 内容与进度分开**：配置表保持只读；收到、已读、已剪、已发货、人物变化等记录到玩家状态，不写回 `data` 表。
- [ ] **C03 条件解释器**：实现当前闭环实际需要的 `dayMin`、`dayMax`、`afterLetter`、`minDelivered`、`worldState`；一封信配置的条件全部满足才出现，缺省条件不作限制。具体世界状态值由文案提供。
- [ ] **C04 条件异常**：未知条件字段、缺失引用或无效阈值要输出明确诊断并阻止该错误内容投放，不能把“不认识”当“已满足”。日志指出信件 ID 和字段。
- [ ] **C05 出现去重**：分别记录未解锁、已解锁可打捞、已收到、已开信；加载存档或收到多个相关事件时，已收到的信不能重新变成候选。
- [ ] **C06 增量内容测试**：由文案添加另一封首信和一个携带现有标签的新词条；系统不改 Lua 也能显示、打捞、剪词和合成。测试后是否保留测试内容由文案决定。

注意：[letters.lua](data/letters.lua) 的注释写了阶段 1 先实现日期条件，但 A9 明确要求世界状态触发后续信。因此不能只实现日期条件就宣告阶段 1 完成。

### 8.2 六个系统分别交什么

| 系统 | 必须产出的能力 | 不放进这个系统的职责 |
|---|---|---|
| Letter | 候选接收、打捞入队、开瓶、已读状态、信件查询与保存 | 决定某种药效会使 NPC 遭遇什么 |
| WordToken | 按位置裁剪、词条实例、来源、已剪位置、复用／消耗状态 | 魔药八步求值 |
| Potion | 草稿投料、容量校验、属性合成、结果与消耗提交 | 订单是否合格、NPC 剧情 |
| Order | 当前订单、逐标签判定、缺项说明、一次性发货记录 | 为副作用作道德判定 |
| WorldState | 从配置建立 NPC 状态、根据发货结果应用后果、输出变化事件与可保存快照 | 硬编码路人甲的信文 |
| Narrative | 解释出现条件、响应跨天／已读／发货／世界变化、解锁后续信 | 在 UI 点击回调里强制发第二封信 |

- [ ] **C07 事件衔接**：沿用 EventBus；裁剪、发货、人物状态变化、解锁信件通过事件联动，页面由对应结果刷新。事件名先对齐 [系统模块设计](../docs/寄往人间_系统模块拆分与依赖设计.md)，不让 UI 直接改另一个系统的内部表。
- [ ] **C08 操作一致性**：同一次裁剪的缺口与库存一起成功；同一次炼制的成品与扣料一起成功；同一次发货的订单、人物变化与解锁记录一起保存，不能恢复出“已寄出但无后果”的半套状态。
- [ ] **C09 生命周期**：退出页面或停止游戏时释放页面监听；切换页面十次不会出现一次点击触发十次事件。

- [ ] **V01 修正入口恢复层级**：入口目前保存 `{ gameFlow = ... }`，却把整个存档传给读取顶层字段的 `GameFlow.Init`；统一保存和恢复的数据层级，并实际验证天数恢复。
