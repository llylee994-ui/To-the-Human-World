Git 实际状态与检查限制只维护在行动记录中。以下新技术约定不改业务规则，不把八种词库定义当成八个已持有词条，也不把原料 price 当成初始库存或订单奖励。

### 1.1 已有公共接口与配置不可误用处

- `Data.Load() -> boolean, string[]`；`GetWord/GetWordByText/GetEffect/GetIngredient/GetEquipment/GetNpc/GetLetter -> table|nil`；`GetCuttableWordsOf(letterId) -> string[]` 按正文标记顺序返回显示文本，没有位置实例 ID。
- Data 的查询目前返回配置原表。调用者只读，不能往配置表写库存、已剪或 NPC 当前状态；也不能把原表直接交给可编辑 UI。
- `GameFlow.Init(saved)` 当前接收的是流程子表；`Serialize()` 返回流程副本。注释写“SaveSystem.Load 返回值”与实际嵌套保存不一致，B1 统一入口处理。
- `SaveSystem.Save(slotName, data) -> boolean, string?`，`Load(slotName) -> data|nil`；当前 Load 无法让调用方区分新开、损坏、版本不支持，旧版本也没有真正迁移。
- `EventBus.On` 的 handler 为 `(eventName, payload)`。通知载荷是普通 Lua table，不是引擎 VariantMap；不能让监听者修改系统内部表。

## 2. 共同类型、单位与错误

本节至第 7 节是拟采用的程序/内容边界。版本只有在真实样板通过校验后才冻结；不能把“提案 v0.1”直接写成已完成的数据版本迁移。

| 类型 | 约定 |
|---|---|
| 定义 ID | 非空字符串，沿用现有 id；引用必须存在，中文显示名不作为主键 |
| 信件实例 | `letterInstanceId` 区别于 `letterId`。阶段 1 首信只领取一次；即使以后允许重复内容也不复用来源实例 |
| 可剪位置 | `spanId` 为稳定字符串；本样板按 body 内 `{{词}}` 出现顺序生成 `body:1` 等。不是中文字符/UTF-8 字节偏移；内容版本改变时不得偷偷重新编号既有存档 |
| 词条实例 | `tokenId` 唯一；`wordId` 是定义 ID，另存来源 `letterInstanceId/spanId/senderId`。同位置只获得一次；reusable 只表示跨次炼制可复用，不等于可凭空复制 |
| 游戏时间 | `GameFlow.day` 为从 1 开始的整数天；药效/服药/工作时间用非负有限 number，单位游戏小时，不驱动现实等待 |
| 服药时间参照 | 所有订单窗口使用“服药时刻=0”的相对小时；`workAfterDoseHours` 是从服药到次晨工作开始的间隔，不是 GameFlow 的第几天 |
| 数值 | 标签权重与 mods 为有限 number；speed 是原始速度修正点，不能直接当小时。intensity/duration/speed/stability/sideEffect 的点数先按现有八步累加，再由配置换算 |
| 货币/库存 | currency 为非负整数金币；原料 quantity 为正整数份，一份占一个原料槽；当前没有价格折现或负库存机制 |
| 布尔/缺省 | false 是有效值，只在 nil 时补允许的缺省。空集合显式 `{}`；缺少必填业务字段不补 0、不补成功，不用 Lua 的 `x or default` 恢复布尔值 |
| 可保存数据 | 仅字符串、有限数值、布尔、纯表；无函数/userdata/循环引用，map 使用字符串键，数组稠密从 1 开始；空数组/对象往返按字段类型识别，不依赖 cjson 自动区分 |

新增计算/命令统一返回以下**判别表**；现有 API 在 B1 由集成层适配，不假装已经具有新签名：

```text
Result<T> = { ok=true, value=T }
          | { ok=false, error={ code, path, message, details={} } }
```

`path` 指向请求或配置字段，`message` 是可显示的中文错误，`details` 保存定位数据。正常字面不合规是 `ok=true, value.canShip=false`，并列出失败条件；配置缺失导致无法判断是 `ok=false`。UI 必须区分二者。

| 错误码 | 触发与后续 |
|---|---|
| CONFIG_MISSING / CONFIG_INVALID / UNKNOWN_ID | 缺字段、错类型/未知条件/引用不存在；阻止受影响流程，反馈给内容方 |
| CONTENT_VERSION_MISMATCH | 基准或待确认版本与当前内容不兼容；保留原档/原待确认，不重新编故事 |
| INVALID_REQUEST / SLOT_LIMIT | 主词数错误、非法份数、槽位超限；保持原配方与库存 |
| TOKEN_UNAVAILABLE / DUPLICATE_TOKEN | 未剪/已消耗/非来源词；同一个 tokenId 同时占多个槽；可复用不允许重复占用同一实例 |
| DUPLICATE_POLICY_MISSING / DUPLICATE_NOT_ALLOWED | 同种原料或同定义不同词条副本重复时，先查明确策略；未配置不能猜允许或禁止 |
| INVENTORY_SHORT / SPECIAL_ITEM_UNAVAILABLE | 缺料或特殊物品不属于本信附件；列出需要量/可用量 |
| ORDER_LOCKED / INVALID_ORDER_STATE / STALE_BASELINE | 待确认禁用操作、状态不符、正式状态版本与基准不一致；不执行部分动作 |
| CONTENT_UNCOVERED / NARRATIVE_CONFLICT / FILL_SOURCE_MISSING / RATING_UNCOVERED | 无事实/片段/评分覆盖或缺来源；不能显示矛盾回信或默认三星 |
| SAVE_ENCODE_FAILED / SAVE_WRITE_FAILED / SAVE_VERIFY_FAILED | 编码、写入、读回核对失败；正式状态和已保存的待确认保持原样 |
| SAVE_CORRUPT / SAVE_VERSION_UNSUPPORTED / SAVE_MIGRATION_REQUIRED | 读档损坏、未来版本、迁移条件不齐；区分新游戏，保留旧文件 |

可选限制缺省代表“该订单明确未要求”，与“首单要求尚未填写”不同：内容校验必须按首单配置包完整性拦截后者。评分缺失、单位缺失、未知条件键均不能静默放过。

## 3. 模块输入输出与唯一状态归属

下列函数名是给后续实现的提案。除第 1 节列出的现有接口外，目前均不存在。默认一名程序开发负责集成，文案负责内容；本表不自动把另一位同伴分配为 Lua 开发 B。

| 模块 | 拟提供公共接口：输入 → 输出 | 独占职责及边界 |
|---|---|---|
| Letter | `PlanReceive(state, letterId)` → 信件状态副本；`GetView(instanceId)` → 三段文本/位置/已剪视图；`PlanMarkCut(state, instanceId, spanId)` → 已剪副本；`PlanArchive(state, followup)` → 归档副本 | 持有队列、收取/阅读/剪裁位置和附件领取记录；直接后续只归档一次，不再次投进打捞队列 |
| WordToken | `PlanCut(state, source)` → 词条状态副本与 token；`ResolveRecipe(state, recipe)` → 已校验词条引用；`PlanConsumption(state, resolved)` → 消耗副本/明细 | 持有来源词实例；按 word.reusable 决定确认时是否消耗，不能改 Letter 内部表 |
| Economy | `PlanSettlement(state, ingredientUses, specialUses, reward)` → 完整账本副本与 delta；`GetSnapshot()` → 账本副本 | 只管金币、材料、特殊物品、已拥有设备；阶段 1 无商店。试算不扣正式库存，不发奖励事件 |
| Potion | `Calculate(resolvedRecipe, config)` → PotionResult | 独立八步计算；不读取/写入别的模块私有状态、不发货、不决定 NPC 后果、不保存 |
| Order | `Evaluate(requirement, potion)` → 判定；`Rate(facts, ratingConfig)` → 星级/反馈；`Accept/BeginBrew/Preview/Confirm/Reset/GetView` | 订单状态、基准与待确认协调；调用上述公开纯计算/副本接口；成功保存全状态后才安装和通知 |
| WorldState | `Simulate(worldSnapshot, potion, context, rules)` → 候选世界、事实、状态差异 | 解释配置的药效影响与人物直接事实；无回信台词、奖励或正式跨天；不对正式世界叠药 |
| Narrative | `ResolveDirect(facts, context, templates)` → 直接后续；`FindAvailable(liveSnapshot, conditions)` → 可出信 ID | 先有事实再选文字；只按正式时间解锁延迟内容。立即回信不会派发 DayStarted |
| GameFlow | 保留 `Serialize/Init`；下一天/计数更新走集成门禁与候选状态 | 唯一维护天数/时段；`deliveredOrders` 作为已确认计数随完整候选保存，事件后不再 +1 |
| SaveSystem | 保留 `Save/Load` 名称；扩展读取状态与可靠写入语义，见第 6 节 | 只读写完整存档，不选择剧情、不各写一个模块文件；保存版本/迁移由集成人统一管理 |

各持有状态的模块后续提供 `ValidateSnapshot(snapshot)`、`GetSnapshot()`、`Restore(snapshot)`（GameFlow 可复用 Init/Serialize）。返回深副本；Restore 安装已校验状态且不广播奖励/发货事件。集成层先验证**所有**模块，再同步安装完整快照，不能读一个模块就立即应用一个模块。

剪词也要完整保存：Letter.PlanMarkCut 和 WordToken.PlanCut 基于同一正式快照产生候选；两部分一起保存成功才安装，再发 WordCut/WordStored。同位置重复请求不新增词条；保存失败既不留空缺也不送词。接单、读信与领附件同理，不能 UI 改一半后再尝试存档。

Order 的命令输入/输出也统一为 Result，具体如下：

| 命令 | 请求 | 成功 value / 前置条件 |
|---|---|---|
| Accept | `{letterInstanceId}` | `{orderId, phase="accepted"}`；信已收到并读过、具有订单，当前没有未完成订单 |
| BeginBrew | `{orderId}` | `{baselineId, phase="brewing"}`；保存首次投料前基准；重复调用返回同一基准，不重拍 |
| Preview | `RecipeRequest` | `{transactionId, phase="pending", view}`；完整字面通过且后果/回信/评分可生成、待确认保存成功。字面失败返回判定 value，phase 保持 brewing |
| Confirm | `{orderId, transactionId}` | `{phase="confirmed", alreadyConfirmed, record}`；同一确认重试返回旧 record，过期 transactionId 不得确认另一次试做 |
| Reset | `{orderId, baselineId, transactionId?}` | `{phase="brewing", baselineId}`；pending 阶段必须匹配 transactionId，重复/过期重置不能撤销已确认记录 |
| GetView | `{orderId}` | 第 3.3 节 UI 视图；只读，不触发保存/重算剧情 |

Preview 的完整字面失败为 `ok=true, value={phase="brewing", requirementResult=...}`；配置/存档失败为 `ok=false`。阶段跳转、baselineId、transactionId 由系统生成，UI 不决定“已经确认”。

### 3.1 投料请求与药效结果

```text
RecipeRequest = {
  orderId, baselineId, equipmentId,
  mainTokenId,
  auxTokenIds = [tokenId, ...],
  ingredients = [{ingredientId, quantity}, ...],
  specialItemIds = [库存物品实例ID, ...]
}
```

原料按 ID 聚合为一行，份数总和占槽；重复聚合行视为非法请求。`quantity>1` 仍属于重复投料，必须检查内容策略。不同 tokenId 引用同一 wordId 的同锅重复策略同样需填写；当前首信各词只有一个实例，不因此阻塞 A～F。

Order 从基准中解析来源、库存、设备拥有权、槽位和重复策略，交给 Potion 纯数据 `resolvedRecipe`；Potion 自身仍校验请求形状及槽数，防止独立调用绕过上限。所有槽位读取 equipment，当前旧锅为 1/2/2/1。

```text
PotionResult = {
  synthesisVersion, contentVersion,
  effects = {标签ID: 最终权重},
  intensityByEffect = {标签ID: 配置中的分级名},
  mods = {intensity, duration, speed, stability, sideEffect},
  durationHours, onsetDelayHours, recoveryAfterEndHours,
  residuals = [{effectId, weight, untilAfterDoseHours}],
  stability, unstable, sideEffects = [{ruleId, addTags}],
  trace = [{step, inputs, outputs, sourceIds}, ...]
}
```

time 字段必须有内容换算来源；residuals 是药效残留，不含已经形成、继续保留的私人记忆状态。缺配置时不伪造完整 PotionResult；只需测试标签层时使用标记为局部计算的夹具，不称为完整可发货结果。

### 3.2 八步计算约定

严格保持 [synthesis.lua](data/synthesis.lua) 注释的次序：

1. 拷贝主词 effects；不得改写 Data.words。
2. 逐个合入辅助词 effects × auxWeight；已有主轴标签的 sameTagBonus 按配置说明加。
3. 并入原料 addTags × auxWeight；份数和重复策略先校验，不凭空享有辅助词同标签奖励。
4. 累加原料五种 mods；无修正的单个键按加法单位元 0 处理，与缺整个必填配置不同。
5. 按 `1 + mods.intensity × intensityScale` 缩放已合并标签。
6. 按配置区间分级；拟采用 `weight <= max` 的首个区间，超过最后边界报配置覆盖错误，不能自造第五档。
7. 按副作用阈值追加标签并记录命中规则，不回到第 5 步再缩放。
8. stability 低于 unstableThreshold 只给提示；阶段 1 不掷随机数、不因为“可能失败”直接吞料。

八步标签/修正计算后才做配置驱动的时间单位转换与订单比较，不改变求值顺序。现有规则还有以下通用语义需在 B3 边界夹具前写清，不能因 A～D 没碰到就暗定：

- 第 2 步“已存在于主轴”指最初主词标签，还是也包括先前辅助词加入的标签；两个辅助词引入同一新标签时会不同。
- 第 7 步副作用加入已有标签时如何叠加，以及第 6 步之后新增/改变标签的显示分级；当前灰烬草可触发 dream，不能漏测此交叉。
- 第 6 步区间端点、极端强度/负权重的允许范围与缺属性换算策略。以上属于内容规则格式补充，确认后写到配置说明。

稳定性沿用现有累计 mods.stability 与阈值比较，不另加未经约定的设备加成或基础稳定性；时间配置也不能插入新的炼药失败步骤。

在规则未完整覆盖前，不宣称任意可选原料/组合已有确定结果；下面 A～F 的确定标签不依赖这些歧义。

### 3.3 字面判定与 UI

```text
RequirementResult = {
  canShip,
  checks = [{id, kind, passed, expected, actual, unit, message}],
  failures = [与 checks 中失败项一致的记录]
}
RatingResult = {stars, feedback, ruleId, factIds}
```

requirement.tags 沿用现有最低权重 map；新增 `conditions` 按声明类型校验。拟支持的首单条件：

| kind | 字段 | 比较/缺省 |
|---|---|---|
| duration | `id, minHours, maxHours` | 闭区间；首单已接受 6～8，必须显式填写 |
| onset | `id, maxDelayHours` | onsetDelayHours 不大于上限；数值待内容方提供 |
| workReady | `id, workAfterDoseHours` | onsetDelayHours + durationHours + recoveryAfterEndHours ≤ 工作间隔；只判药效结束/恢复时间，不推断剧情中的能力 |
| residualAt | `id, effectId, atAfterDoseHours, maxWeight` | 对配置药效残留曲线/区段采样；采样边界与残留表由内容方明示 |
| forbiddenEffect | `id, effectId, maxWeight` | 只限制订单明确禁止的标签，不自动禁止所有额外效果 |

`conditions` 不得用任意 Lua 表达式或函数字符串；遇未知 kind 返回 CONFIG_INVALID。首单需要的 onset/workReady/residualAt 不能因旧表没有字段就当“不限制”。没有明确禁止效果的订单可配置空禁用集。

Order.GetView 返回深副本：当前阶段、正式/试做库存、配方、药效、每项判定、待确认回信与评分，以及 `actions={操作名:{enabled,reasonCode,message}}`。所有命令在模块入口复查门禁，不能只把按钮灰掉。调试下一天/读取等入口也须走同一协调流程。

## 4. 内容负责人要填写的配置包

通过既有 `data.content` 暴露新增表，不让各系统直接 require 新分表。以下按字段交接，具体新增文件名由内容负责人安排；本轮不创建这些运行配置，也不改 content.lua。

### 4.1 字段清单与已知值

| 位置（提案） | 类型/含义 | 当前状态与填写要求 |
|---|---|---|
| `Data.contentVersion` | 非空字符串，整包内容修订标识 | 新增；与 synthesis.version 和存档 schema 分开。基准/待确认均保存它 |

### 4.2 事实、片段与评分最小结构

为避免系统硬编码 NPC 特例，规则统一使用有类型的字段与条件。条件数组表示全部满足；首单只需要明确的比较运算 `eq/ne/gte/lte`。输入只允许白名单 `potion.effects`、`world.npcs`、`context`、`facts` 的已声明字段，不求值自由代码。

```text
DirectRule = {
  id, ruleSetId, priority,
  when = [{source, path, op, value}],
  unless = [{source, path, op, value}],
  facts = [{id, subjectId, objectId, value, important}],
  changes = [{path, op="set"|"add", value}]
}
Fragment = {
  id, templateId, kind="key"|"combination"|"single"|"generic",
  priority, exclusiveGroup,
  requiresFacts=[factId,...], excludesFacts=[factId,...],
  coversFacts=[factId,...], overrides=[fragmentId,...],
  text, bindings={占位名:{source,path}}
}
FollowupTemplate = {
  id, letterId, opening, closing, baseFragmentIds,
  fragmentIds, fallbackFragmentIds
}
RatingRule = {
  id, ratingSetId, priority, // 仅同星级内按 priority 降序、id 升序选择
  requiresFacts, excludesFacts, stars, feedback
}
```

条件/事实 ID/状态字段由内容方定义并校验引用。when 全部满足、unless 任一满足则排除；requiresFacts 全部必须存在、excludesFacts 任一存在即排除。缺字段不当 false 比较通过。所有事实规则针对**同一输入快照**匹配，再汇总更改；DirectRule 不读取同批其他规则尚未生成的事实，facts 作为下游 Narrative/Rating 的输入。同一字段冲突 set、事实互斥同时成立则报配置冲突，不按偶然遍历顺序覆盖。add 仅用于已声明数值字段。

WorldState 输出事实记录需加 `sourceRuleId`、药效/人物输入依据；不靠片段反推事实。私人记忆 `objectId` 必须存在且限于内容指定对象；遗忘产生的持久状态不在药效计时结束时自动清除。dream 不生成真实证据。内容方应声明事实互斥组，防止同时“认清母亲”与“无法认清”。

Narrative 顺序为关键定制 → 组合 → 单效果 → 通用；同档按 priority 降序、id 稳定排序。overrides 仅覆盖被指定的片段，exclusiveGroup 只保留一个兼容片段。缺填充值时尝试事实兼容且覆盖必要事实的 fallback；仍有 important 事实未表达或有占位符残留，则 CONTENT_UNCOVERED，不能展示待确认。

Rating 由 Order 在直接事实与人物认知已解析后选择匹配规则，依据[身份与评分规则 §七](../docs/设计/寄往人间_五类玩家身份与结局判定规则.md)，**先匹配三星，再二星，最后一星**。stars 只能为 1、2、3；priority 降序、id 升序只用于同星级内的稳定选择。低星规则即使 priority 更高或 ID 更靠前，也不能压过已匹配的高星规则；互斥条件由事实与配置处理。

内容方必须提供有事实来源、覆盖合法剩余结果的一星反馈。合规订单未命中二/三星属于正常情况，应匹配配置中的一星规则，不能直接报错，也不能由程序凭空补一个星级或反馈句。RATING_UNCOVERED 仅用于评分配置缺失、没有合法规则/反馈覆盖等内容错误；反馈缺少事实来源或填充来源时报告 FILL_SOURCE_MISSING，不伪造来源或降到其他星级掩盖错误。整包校验检查一星覆盖，不能只验证 A～D 的高星分支。

D 必须有本人难受的事实，不能用 forget>0 一概扣星。反馈与 ruleId/factIds 一起保存；报酬来自订单的固定 reward，与评分函数无关。字面不合规仍不可发货或评分；本次只修正交接契约，不表示评分系统已实现。

评分交接样例（均为已满足字面条件、事实条件已匹配的规则；数字 priority 和规则 ID 仅为排序夹具，不是剧情配置）：

| 用例 | 输入/条件 | 期望 |
|---|---|---|
| R1-1 跨星级优先 | 三星 `z_three` priority=10；一星 `a_one` priority=100 | 选三星，低星 priority/ID 均不能抢先 |
| R1-2 二星优先 | 没有三星匹配；二星 priority=10，一星 priority=100 | 选二星 |
| R1-3 合法一星覆盖 | 没有二/三星匹配；一星规则匹配且反馈/事实来源完整 | 返回配置的一星和反馈，不报 RATING_UNCOVERED |
| R1-4 缺少覆盖 | 没有高星匹配，且缺一星规则、反馈为空或没有合法反馈覆盖 | 报 RATING_UNCOVERED，不能产生待确认评价 |
| R1-5 缺少来源 | 命中的一星反馈需要某事实/填充值，但来源未提供 | 报 FILL_SOURCE_MISSING，不编造反馈 |
| R1-6 同星级 priority | 同为二星，两规则 priority=10/20 | 选 priority=20；与输入排列顺序无关 |
| R1-7 同星级 ID | 同为二星、priority 相同，ID 为 `a_two`/`z_two` | 选 `a_two`；与输入排列顺序无关 |

所有成功案例的同单报酬均为同一个配置值 R；失败案例不能生成新评价或结算奖励。首单 A/B=3、C=2、D=1 的预期保持不变，仍需真实配置与运行验证。

### 4.3 现有校验缺口与填写顺序

现有 Data.Load 仅查部分引用，不是完整 schema 校验：缺 senderId、缺 requirement.tags、effects/mods 类型错误、数量为负/非整数等并非都能拦住；对每封信一律要求正文可剪标记和 requirement，也容纳不了纯直接回信。

内容负责人按以下顺序落盘：

1. 保持旧 ID 与 `{{词}}` 文本对应；首信位置顺序为：累、快乐、忘记、梦、安静、睡觉。统一 NPC“独居”与首信“和妹妹同住”的冲突，程序不擅选一方。
2. 加入 kind 与 cuttable，按信件类型校验：order 必须有订单条件；direct_followup 不要求可剪标记或新订单，不进入普通出现队列。待确认禁剪/禁附件仍由运行门禁保证。
3. 填初始账本、固定报酬、时间属性 profile、重复策略；将已接受的初值显式落盘，新增字段用类型/取值范围/引用存在性校验。
4. 落 NPC 初态、事实规则、第二封逻辑信、模板片段、评分与来源，补齐 D 的本人难受反馈。检查模板引用、互斥、组合覆盖、无填充值路径；评分按三星→二星→一星验证，确保一星规则有来源并覆盖未命中高星的合法剩余结果。
5. 补 `Data.ValidateStage1() -> boolean, string[]`（拟新增），在旧 Data.Load 基础上检查整个首单包齐备和条件覆盖；入口必须检查返回结果，缺配置显示具体路径并阻止开局/受影响操作。
6. 把 A～F 和原料差异样例落成固定输入/期望数据，程序验证后共同冻结 contentVersion。当前配置允许阶段 0 校验通过，不代表 ValidateStage1 已通过。

## 6. 完整存档与一次确认协议

### 6.1 当前 v1 与拟议 v2

当前真实写出的是 `{schema=1,data={gameFlow=GameFlow.Serialize()}}`，启动却把 `data` 整体传给 GameFlow.Init。拟将阶段 1 的完整数据升到 schema=2；**本轮不改常量，不迁移真实存档**。

```text
EnvelopeV2 = {schema=2, data={
  contentVersion,
  revision,                // 所有成功保存的正式状态变更递增；读操作不递增
  nextOrderSerial,          // 下一订单实例序号，分配时一起保存
  live=LiveState,
  currentOrder=false | CurrentOrder
}}
LiveState = {
  gameFlow,                // 原有五个字段
  letters={byId, bottleQueue, directArchive},
  wordTokens={byId},       // 来源/可用状态；规则仍读 words.reusable
  economy={currency, ingredients, specialItems, ownedEquipmentIds},
  world={npcs, flags},
  narrative={unlockedLetterIds, delayedQueue, resolvedEventIds},
  orders={acceptedById, confirmedById}
}
CurrentOrder = {
  orderId, letterInstanceId,
  phase="accepted"|"brewing"|"pending",
  baseline=false | {id, revision, contentVersion, live=LiveState},
  recipe=false | RecipeRequest,
  pending=false | {
    transactionId, status="pending", contentVersion, synthesisVersion,
    potion, requirementResult, facts, worldChanges,
    followup={letterId, fragmentIds, bindings, renderedText},
    rating={stars, feedback, ruleId, factIds},
    consumption={ingredients, consumedTokenIds, specialItemIds},
    reward={currency},
    candidateLive=LiveState
  }
}
```

schema 是文件结构版本，contentVersion 是内容包，synthesisVersion 是计算规则；三者不混用。所有 `false|对象` 字段必须显式存 false，不用 JSON null 或省略来区分“无对象/损坏字段”。accepted 阶段 baseline/recipe/pending 为 false；brewing 有 baseline；pending 三者齐全。任何不一致都禁止半恢复。

`orderId` 由存档分配的单调序号生成；`baseline.id` 在首次投料前固定；`transactionId` 对应本次待确认，重试确认沿用同一个 ID。重置后新试做可有新 transactionId，但同一基准/规范化配方的计算不依赖这个 ID或当前时钟。必要的随机种子必须来自已保存基准；阶段 1 无随机失败。

`confirmedById[orderId]` 保存 transactionId、来源信、配方/药效、事实、回信、评分、消耗/奖励及内容版本。候选已包含全部正式变化：信件归档、词条消耗、账本、人物、队列、完成数和订单记录；它是纯 LiveState，不再包含 currentOrder/基准，避免递归嵌套。

核心集合的条目格式也需固定，避免两人各存一份不同结构：

| 字段 | 条目/键 |
|---|---|
| letters.byId | 以 letterInstanceId 为键；`{letterId,senderId,received,read,cutSpans={spanId:true},claimedAttachmentIds}`，状态布尔明确保存 |
| letters.bottleQueue | 稠密 letterInstanceId 数组，无重复；实例指向配置 ID，不在队列复制可变信件对象 |
| letters.directArchive | 以 orderId 为键；`{transactionId,letterId,renderedText,fragmentIds,rating}`，从确认记录投影，加载时验证一致 |
| wordTokens.byId | 以 tokenId 为键；`{wordId,sourceLetterInstanceId,sourceSpanId,sourceNpcId,available,consumedByOrderId=false或ID}`；来源位置一对一，显示名/类别从相容版本内容读 |
| economy.ingredients | 以 ingredientId 为键的非负整数；specialItems 以实例 ID 为键保存 `{itemId,sourceLetterInstanceId,available}`，ownedEquipmentIds 为 ID→true 集合 |
| world.npcs | 以 NPC ID 为键的已声明字段 map；world.flags 为已声明世界字段 map，类型/范围来自内容 |
| narrative.delayedQueue | `{eventId,sourceOrderId,conditionId}` 数组；其余解锁/已执行集合为 ID→true，不能靠重读回信增加 |
| orders.acceptedById | 以 orderId 为键；`{letterInstanceId,letterId,acceptedDay}`；confirmedById 使用上文完整确认记录 |

profile 的 residualRules 尚需内容方补齐“何时仍残留、残留多少”的数值表及端点，当前没有依据将它简单视为持续时间结束即为零；实现不得隐式采用此假设。

读档必须校验候选差异只包含本单允许更改、扣料/奖励与明细一致、来源词和剪裁标记一致、确认记录唯一、发货计数与确认记录一致；结构“长得像”不够。旧 v1 的历史计数另见迁移规则，不用不存在的记录填平。

### 6.2 状态转换与失败时机

1. **接单/剪词**：先完成正式状态保存。首次投料请求到来前，BeginBrew 保存包含当前正式状态的基准，成功后才接受第一份材料。失败保持 accepted，不进入试做。
2. **炼制**：所有消耗均从基准副本计算，正式账本不动。若其他正式变更使 revision 不等于 baseline.revision，报 STALE_BASELINE，不能覆盖其进度；须先恢复/重建一致的操作流程，不静默换基准。影响本单的修改由集成门禁约束。
3. **发货预览**：先检查全套字面条件，再算候选人物事实、回信、评分和完整结算。任何一环失败都保持原正式状态，不展示可确认的假结果；成功保存 `live=S0 + pending=PA` 后才派发 DeliveryPreviewReady 并展示。
4. **待确认**：允许查看、确认、重置；禁止下一单、购物、跨天、剪后续词、领取附件。其他会改变基准的正式写操作也不能绕过门禁；只能返回具体禁用原因。
5. **确认**：先检查 confirmedById 实现幂等；验证整份候选，用一次完整保存写入 `live=candidateLive,currentOrder=false`。保存失败保留 S0/PA，不广播正式事件。成功后同步安装所有模块快照，再通知；安装过程禁止嵌套命令/再次确认。
6. **重置**：保存 `live=baseline.live`，currentOrder 回 brewing，保留同一 baseline、recipe/pending 置 false；成功后安装再通知 DeliveryReset。保存失败仍保留原 PA，不先关闭结果窗口。
7. **退出/重进**：读取保存的 PA，不重算模板/星级、不自动确认。保存成功后、通知前崩溃时，下次读档使用已确认 S1；不重播用于结算的事件，不再次发奖。

后续正式通知 `PotionDelivered/OrderRatingRecorded/MoneyChanged/ItemRemoved/NpcStateChanged/LetterArchived` 等均仅供刷新/观察，载荷带 orderId、transactionId、revision、必要结果副本。任何会影响奖励/世界/队列/身份计数的动作都已在候选里算完，不能挂在通知监听器里二次执行。监听器失败只表示通知失败，不能把已落盘确认说成未确认。

### 6.3 Save/Load 的实现约束与迁移

- 保留 `Save(slot,data)` 的第一个 boolean 返回值，第二值扩成结构化错误并更新调用者；整个 data 对应上面的 Envelope.data。B1 应补 `Load(slot) -> data|nil, status`，status 明确 `new/loaded/migrated/corrupt/unsupported/migration_required`，必要时带 error。
- 先校验/保护性编码，再写；当前代码先用 FILE_WRITE 打开正式路径、后编码，且不检查 WriteString 返回值，不能支撑失败不损档承诺。应在实现前选定并实测临时文件+替换或双槽完整快照方案，保留最后一个已验证存档，不在文档中假定重命名跨平台原子。
- 引擎 File 路径为项目/用户隔离的相对路径，使用全局 cjson；不能用 io、os.rename 或绝对用户目录。File.WriteString 及读回结果需检查；“文件能打开”不等于整个保存成功。
- `Save` 成功必须表示约定读回校验完成、下次 Load 能选择新快照；任一步失败返回失败，旧 S0/PA 可恢复。实际文件协议、写入中断/读回失败测试属于 B1，实现后再冻结此部分，不以模拟保存器代替。
- v1 正式入口档识别 `data.gameFlow`，只把子表交给 GameFlow。历史 SelfTest 的扁平 `{day=...}` 属于 selftest 槽，不应为了让测试过就猜正式档结构；如发现真实旧格式，补明确迁移分支和样例。
- v1→v2：保留合法流程字段（包括 false），新系统用已校验的首单初态补齐；无完整内容配置时返回 migration_required，不把货币猜成 0。若 v1 已有非零 deliveredOrders，却无订单明细，返回迁移待处理，不伪造完成记录。
- 新开仅指文件不存在。损坏/未来版本不覆盖原文件；可展示错误并回到安全入口，但不能继续自动保存成新档。恢复全部模块成功后再发送一次 SaveLoaded 刷新界面。
- 不兼容内容版本的待确认结果不能偷偷重算；保留原档，提示迁移/恢复对应内容。具体内容版本兼容迁移逐项提供，不能靠默认值吞掉基准/待确认。
