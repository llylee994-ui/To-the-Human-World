# 《寄往人间》前端接入接口手册

> 版本：v0.1，2026-10-05。代码基线：`fengyycon@207f5c6`，已与 `github/main` 对齐。
> 本手册描述该版本的**实际代码**，不是新增 API 提案。内容版本当前为 `story-v0.4-r1`，生产存档 schema 为 2；新文案、剪词和属性尚未全部接入。
> 接入范围：打捞、读信、剪词、词卡/材料、炼药、直接后续、确认/重置与恢复。正式美术尚未接入。

## 1. 接入结构与边界

这里的后端是设备内 Lua 游戏逻辑，没有 HTTP 地址、请求头或服务端部署。调用 Lua 函数即调用业务接口。

```text
界面控件 / 动画 / 点击区域
  ├─ PlayModel：导航、选料、提示和业务命令封装
  ├─ 只读查询：信件视图 / 词卡视图 / 订单视图 / 状态快照
  └─ GameSession → GameState / Order → 保存完整候选 → 安装状态 → 事件通知
```

- 生产装配：[GameSession.lua](core/GameSession.lua)；入口：[main.lua](main.lua)。界面使用当前会话，不能每页创建一个新会话或自行恢复模块。
- 当前可运行参考：[PlayView.lua](ui/PlayView.lua)、[PlayModel.lua](ui/PlayModel.lua)。正式界面优先复用交互封装，新增展示组件可以拆分。
- `GetGameSession()` 由 main 暴露。应在现有初始化/读档完成后取得；优先像 `PlayView.New(session, content, enabled?)` 一样由集成入口传入。
- 内容查询使用已加载的 `data.content`。不要由每个页面重复 `Data.Load()`；不得修改内容查询返回的配置表。
- UI 只保存导航、滚动、动画和选料等显示状态，不直接写库存、世界、词卡、订单或存档。
- 新页面需要同一会话、同一存档槽。读档/新开游戏属于入口职责；恢复按钮调用 `ReloadCurrent()`，不能用省略参数的 `Load()` 冒充同槽恢复。
- 本手册不授权修改 data、剧情或规则。草稿中的药效、价格、数量与位置不代表运行配置已定稿。

## 2. ID、返回值与显示规则

### 2.1 不同 ID 不可混用

| 标识 | 含义 | 来源与使用 |
|---|---|---|
| `letterId` | 配置中的信件定义 | 可打捞列表返回；传给 ReceiveLetter |
| `letterInstanceId` | 已收到的信件实例 | ReceiveLetter 返回；读信、剪词、接单使用 |
| `spanId` | 一封信中的可剪位置 | `GetView().value.spans` 返回；不是像素坐标或字符偏移 |
| `wordId` | 词条定义 | 用于查询文字和分组；不能代替具体卡片投料 |
| `tokenId` | 一张有来源的词卡 | 库存视图返回；主词/辅词投料使用 |
| `orderId` | 一份订单 | Accept 返回或从当前订单读取 |
| `baselineId` | 首次投料基准 | BeginBrew 返回；请求中的字段名为 baselineId，快照中为 `baseline.id` |
| `transactionId` | 一次成功生成的待确认结果 | Preview 返回或 `pending.transactionId`；确认/重置必须使用当前值 |

虽然当前实例 ID 有可读格式，前端也必须把 ID 当作不透明字符串；不靠拼接或解析 ID 获得业务事实。同名词卡按来源分别保留；库存可以分组展示，选择仍落到具体 tokenId。

### 2.2 返回约定

大部分业务命令和业务视图返回：

```lua
{ ok = true, value = ... }
{ ok = false, error = { code = "...", path = "...", message = "...", details = {} } }
```

以下是实际例外，不要统一按 `result.value` 取值：

| 接口 | 返回 |
|---|---|
| `session.state.GetSnapshot()` | 完整状态副本或 nil |
| `session.state.GetStatus()` | 状态对象，含 status，错误时可有 error |
| `session.state.CanMutate()` | boolean，仅为全局可变更性，不替代具体操作校验 |
| `session.state.CheckAction(name)` | `{enabled, reasonCode, message}` |
| `session.state.Load(slot)` / `ReloadCurrent()` | 两个值：`data, status`；失败 data 为 nil |
| `session.state.Save(slot)` | `ok, error?`；普通页面不应自行另建保存流程 |
| `model.Refresh()` / `GetDraft()` | 状态或草稿副本，非 Result |
| `model.Navigate(page)` | 修改导航状态，无业务 Result |
| `content.GetLetter/GetNpc/GetWord(id)` | 定义表或 nil，按只读使用 |

`ok=true` 不是“这单成功”：合法试配但不满足字面要求时，Preview 仍返回 ok=true，phase 为 brewing。通知异常可作为 `value.notificationErrors` 返回，此时业务可能已成功，不能重复结算。

### 2.3 不应展示的内部信息

- 词卡正常显示字面、类别、数量与来源；不展示属性权重或功能型说明。
- 订单要求单独读取 `definition.requirement.desc`，报酬读取 `definition.reward.currency`。不要从正文加粗或词卡文字推断条件。
- 调试页当前展示的药效原始数值不自动成为正式美术要求；保留玩家需要的药效、强度描述、时间和失败原因。
- 原始错误路径、事务号和存档文件名供日志定位，正式界面应给可理解提示。

## 3. 只读查询与页面映射

### 3.1 全局快照

```lua
local data = session.state.GetSnapshot()
-- 必须先确认 data 存在且读取/配置状态正常
-- data.live.gameFlow.day / phase / canSalvage / deliveredOrders
-- data.live.economy.currency / ingredients / specialItems / ownedEquipmentIds
-- data.live.letters.byId / bottleQueue / directArchive
-- data.live.wordTokens.byId
-- data.live.orders.acceptedById / confirmedById
-- data.currentOrder == false，或 {orderId, letterInstanceId, phase, baseline, recipe, pending, ...}
```

只读使用，即使返回副本也不要把修改后的副本直接塞回模块。`currentOrder=false` 表示没有当前订单；不能访问 `false.phase`。

### 3.2 可打捞列表

```lua
local result = session.modules.narrative.FindAvailable(data.live)
-- Result<letterId[]>，不是已收到的瓶子队列
```

当前支持 `appearCondition.dayMin/dayMax`；额外 conditions 只接受 nil 或空表，复杂世界条件不能自行传入。结果排除已经收到的信件。候选列表不代表此刻允许收取，还要看 `CheckAction("ReceiveLetter")`、`gameFlow.canSalvage` 和时段；最终 ReceiveLetter 再验证。

### 3.3 信件视图

```lua
local result = session.modules.letters.GetView(letterInstanceId)
```

订单信 value：`letterId, kind, cuttable, selfIntro, address, segments, spans, instanceId, received, read, claimedAttachmentIds`。

- 普通片段：`{kind="text", text=...}`。
- 可剪片段：`{kind="word", spanId, wordId, text, cut, canCut}`。
- `segments` 按显示顺序排列；`spans` 列出可剪位置。同一位置可能在两个数组出现，不代表两张卡。
- 剪后不直接显示原片段 text，改用缺口；周围文字和位置身份保持。触摸区域可扩大，剪词请求仍只传一个 spanId。
- `span.canCut` 仅表示已读且未剪；实际操作还受 `CheckAction("CutWord")` 限制。
- 已确认直接后续可用对应 orderId 查询归档，返回 `{orderId, kind="direct_followup", cuttable=false, archive}`；与订单信结构不同。
- 标题、寄信人由定义和 NPC 查询补充：`content.GetLetter(view.letterId)`、`content.GetNpc(definition.senderId)`。
- 目前没有已实现的独立 signature、emphasis、收信时固定正文变体字段。新稿三段排版与加粗可做组件设计，但实际接入先完成新契约；不能把 Markdown `**` 直接当已支持格式。

### 3.4 词卡库存视图

```lua
local result = session.modules.wordTokens.GetInventoryView()
```

value：`cards, groups, availableCount, availableDefinitionCount, availableCategoryCount`。

- card：`tokenId, definition, source, available, consumedByOrderId`。
- source：`wordId, sourceLetterInstanceId, sourceSpanId, sourceNpcId`。
- group：`wordId, definition, collectedCount, availableCount, availableTokenIds`。
- cards 保留历史已消耗卡；可投料列表筛 `available=true`。group 的剩余张数只数可用卡。
- 卡片选择不得按 wordId 随意拿第一张，要明确玩家选择的来源卡。

### 3.5 订单视图

```lua
local current = session.order.GetView() -- 当前订单或 idle
local history = session.order.GetView({orderId = confirmedOrderId})
```

当前视图含 `phase, formalInventory, actions`，有当前订单时再含 `orderId, baseline, recipe`；pending 时还含 `pending, trialInventory`。

历史已确认视图是 `{phase="confirmed", orderId, record, actions={}}`，不能假设所有字段与当前视图相同。

`pending` / `record` 中展示所需的主要字段：

| 字段 | 展示用途 |
|---|---|
| `potion.effects` / `intensityByEffect` | 已算出的药效与强度描述；名称从效果配置读取 |
| `potion.onsetDelayHours` / `durationHours` | 发作延迟 / 持续时间，单位小时 |
| `requirementResult` | 字面条件是否满足与具体原因 |
| `followup.renderedText` | 已生成且保存的直接后续正文 |
| `rating.stars` / `rating.feedback` | 一至三星及人物反馈 |
| `consumption.consumedTokenIds` | 将消耗/已消耗的来源卡 |
| `consumption.ingredients` / `specialItemIds` | 原料份数与特殊物品 |
| `reward.currency` | 本单固定报酬 |
| `transactionId` | 确认/重置请求凭据，不显示给玩家 |

`trialInventory` 是确认后的候选账本，不可提前作为主页真实金币/库存。已确认后续读取 record；不重新调用生成器编写一次新结果。

## 4. 优先复用的前端操作封装：PlayModel

创建一次并在同一界面生命周期内复用：

```lua
local PlayModel = require "ui.PlayModel"
local model = PlayModel.New(session, content, enabled)
-- enabled 可选；若当前入口传入隔离调试保护，正式页面必须保留该保护
```

| 调用 | 作用 / 返回 |
|---|---|
| `model.Refresh()` | 同步会话状态与选料关联，返回状态副本或 nil |
| `model.Action(name)` | 操作开关与原因，并包含入口的 enabled 保护 |
| `model.Navigate(page)` | 导航；现有 page 为 mail / letter / words / brew / result |
| `model.Receive(letterId)` | 收信；成功记住 selectedLetter，不自动标已读 |
| `model.Read(instanceId)` | 首次读信调用业务命令；已读信只切换阅读，不重复写档 |
| `model.Cut(spanId)` | 对 selectedLetter 剪词 |
| `model.Accept()` | 接 selectedLetter 的订单，成功进入 brew |
| `model.Edit(kind, id?, delta?)` | 校验和修改投料草稿；首次有效投料会保存基准 |
| `model.GetDraft()` | 返回当前投料副本 |
| `model.CancelBrew()` | 条件允许时退回剪词准备，清空草稿 |
| `model.Preview()` | 使用当前草稿；pending 时进入 result，字面失败保留 trialPotion/failure |
| `model.Resolve(true)` | 从当前 pending 构建正确凭据并确认 |
| `model.Resolve(false)` | 从当前 pending 构建正确凭据并重置，返回 brew |
| `model.NextDay()` | 请求跨天 |
| `model.Reload()` | 同槽恢复；pending 自动进入 result，否则进入 mail；清临时选料和试做显示 |

上述业务操作返回 Result。显示状态包括 `page, selectedLetter, selectedResult, message, dirty, failure, trialPotion`。

### Edit 的已实现种类

```lua
model.Edit("equipment", equipmentId)
model.Edit("main", tokenId)
model.Edit("aux", tokenId)
model.Edit("removeMain")
model.Edit("removeAux", tokenId)
model.Edit("ingredient", ingredientId, 1)  -- 放入一份
model.Edit("ingredient", ingredientId, -1) -- 移出一份
model.Edit("clear")
```

特殊物品投料的 Edit 分支尚未提供，不可照名称猜一个 `special` 调用。界面拖入锅中只是触发相应 Edit；最终以返回结果更新物件，不能靠拖拽动画永久扣库存。

### 渲染更新

- 当前 PlayView 在 Update 中检查 `model.dirty`，再重建内容；点击回调期间不销毁正在派发事件的控件。
- 单纯 Navigate 只改变显示，不会确认、重置或释放订单限制。
- 若正式页面自订阅事件，订阅/退订要跟随页面生命周期；事件只触发读取/刷新，不再结算。
- 选料草稿主要在 PlayModel 内；BeginBrew 保存基准，不等于每次 Edit 都把完整选料保存。已有 pending 的配方和后续会持久保存。不得承诺退出后完整恢复任意尚未 Preview 的临时草稿。

## 5. 底层业务命令（需要直接接入时）

### 5.1 信件命令

| 接口 | 请求 | 成功 value / 前提 |
|---|---|---|
| `session.state.ReceiveLetter` | `{letterId}` | `{letterInstanceId, changed, revision, notificationErrors?}`；首次必须在可打捞列表且允许打捞 |
| `session.state.ReadLetter` | `{letterInstanceId}` | 同上；必须已收到 |
| `session.state.CutWord` | `{letterInstanceId, spanId}` | 上述字段加 `tokenId, source`；已读、合法位置 |

合法重复收取/已读/同位置剪词在允许的阶段返回 `changed=false`，不新增物品或事件；已锁定阶段会先拒绝变更，不应依靠重复请求绕过限制。剪词成功的缺口与词卡是同一次保存，不分两次更新正式状态。

### 5.2 订单命令

| 接口（session.order） | 请求 | 成功 value / 限制 |
|---|---|---|
| `Accept` | `{letterInstanceId}` | `{orderId, phase, alreadyAccepted}`；收到并读过订单信，当前无另一未完成单 |
| `BeginBrew` | `{orderId}` | `{orderId, baselineId, phase}`；保存首次投料基准，重复使用原基准 |
| `CancelBrew` | `{orderId}` | `{orderId, phase="accepted", alreadyPrepared}`；仅从未生成 pending、从未重置的当前单 |
| `Preview` | RecipeRequest | 字面不合规：`{orderId, phase="brewing", requirementResult, potion}`；合规且保存成功：`{orderId, transactionId, phase="pending", potion}` |
| `Confirm` | `{orderId, transactionId}` | `{orderId, transactionId, phase="confirmed", alreadyConfirmed, record}`；同一已确认事务重试不再结算 |
| `Reset` | `{orderId, baselineId, transactionId?}` | `{orderId, baselineId, phase="brewing", alreadyReset, transactionId?}`；pending 必须传当前 transactionId |

成功 Preview 的返回没有直接携带完整 followup/rating；随后调用 `GetView()` 读取保存的 pending。不要照旧提案读取不存在的 `value.view`。

```lua
local recipeRequest = {
    orderId = currentOrder.orderId,
    baselineId = currentOrder.baseline.id,
    equipmentId = selectedEquipmentId,
    mainTokenId = selectedMainTokenId,
    auxTokenIds = selectedAuxTokenIds,
    ingredients = { { ingredientId = selectedIngredientId, quantity = 1 } },
    specialItemIds = {},
}
```

此段是请求结构示意，变量由当前状态和玩家选择提供，不是固定配方。原料同 ID 聚合成一行；每份占一槽。设备容量与同名词/原料重复策略读取配置，不在 UI 写死。

### 5.3 跨天与恢复

- `session.state.NextDay()`：Result，生产成功 value 至少有 `day`；accepted 阶段可跨天，brewing/pending 禁止。
- `session.state.ReloadCurrent()`：`data, status` 两个返回值，失败 data=nil。恢复已保存的 pending 后应引导回决定页。
- `session.state.GetStatus()`：读取 new/loaded/migrated 或错误状态；不要把读取失败当作新开游戏，更不能覆盖旧档。

## 6. 操作阶段和禁止事项

| 阶段 | 前端应该表现什么 | 关键限制 |
|---|---|---|
| idle | 没有当前订单，允许按条件打捞/读信/剪词/接单 | 是否有内容与资源仍需查询 |
| accepted | 已接单，尚未建立炼药基准 | 可继续剪词或跨天；不能再接另一单 |
| brewing | 已建立首次投料基准，正在试配 | 禁止收信、首次标已读、剪词、跨天和接新单；已读信可只读查看 |
| pending | 已保存药效和后续，等待决定 | 不能换料，须确认或重置；切页不能解除限制 |
| confirmed | 通过历史查询查看已确认结果；currentOrder 已为 false | 只读重看，不重新发奖或生成后续 |

`CheckAction(name)` 是粗粒度操作门禁，不保证具体请求一定成功。例如 GetView 的 span.canCut=true 仍可能被订单门禁禁止；库存不足、过期事务、未知 ID 仍需命令验证。

重置不是整局重开，也不是回到收信之前：保留首次投料前已剪词、已接订单和以前确认的成果。重置后保持 brewing，并不恢复剪词权限；首次尝试尚未产生后续时可以另用 CancelBrew 回准备。

剪词、读信等命令和订单操作会自行保存。确认前 UI 可以展示“将消耗”“预计报酬”，不能把候选余额覆盖正式余额。奖励、物品变化等事件只是通知，不是再执行一次扣费的入口。

## 7. 错误处理

| 情况 / 代表代码 | 前端行为 |
|---|---|
| `ORDER_LOCKED` / `INVALID_ORDER_STATE` | 提示当前应完成的步骤，保留当前内容 |
| `INVENTORY_SHORT` / `TOKEN_UNAVAILABLE` / `DUPLICATE_TOKEN` / `SLOT_OVERFLOW` | 拒绝该次选择，刷新库存或容量，显示可理解原因；这些代码来自现有交互层，底层也可能返回更具体代码 |
| 字面不合规，但 Preview ok=true | 显示 potion 与 requirementResult.failures，允许调整；无消耗、无后续、无发货 |
| `CONFIG_INVALID` / `UNKNOWN_ID` / 内容覆盖错误 | 提示内容不可用并记录详细错误，不补默认成功 |
| 已明确的 `SAVE_WRITE_FAILED` | 保留操作前状态/待确认，提示本次未生效、可排除存储问题后重试 |
| `recovery_required` / `COMMIT_RECOVERY_REQUIRED` / error.details.committed | 结果可能已提交；锁定写操作，使用同槽恢复核对，不一概宣称“未生效”或再次发奖 |
| `migration_required` / corrupt 等加载失败 | 保留旧文件，显示恢复限制，不暗中清档 |
| 成功结果带 notificationErrors | 正式结果已保存时不得回滚或重发；读取状态并记录通知异常 |
| `NOT_IMPLEMENTED` | 未实现入口不对玩家表现成可完成操作 |

错误码举例不是穷举白名单。未知错误也必须保留原状态并显示适当提示；具体 path/details 留给日志。

## 8. 主页物件如何映射真实状态

| 主页元素 | 真实数据依据 | 显示/操作规则 |
|---|---|---|
| 海上的漂流瓶 | `FindAvailable(data.live)` | 成功列表为空才无瓶；查询失败不能假装空海。禁用打捞时可保留瓶子并关闭操作 |
| 桌上未开瓶 | `live.letters.bottleQueue` 引用的 byId 项且 `read=false` | 已收未读；Receive 成功后出现，Read 成功后换成信纸表现 |
| 已读信件 | 已收到实例且 `read=true` | 展示选中信件或设计约定的堆叠；首页选择优先级属于 UI 方案，尚无后端“当前首页信件”字段 |
| 当前订单标记 | `currentOrder` / acceptedById / confirmedById | 区分未接单、已接、试配、待确认与历史；信件已读不等于已完成 |
| 待决定的结果物件 | `currentOrder.phase=="pending"` | 引导去后续页；不代表获得一瓶可自由出售的库存药水 |
| 词条托盘 | `GetInventoryView().value.cards/groups` | 空/有词；只用可用卡供投料，已消耗卡另作历史展示 |
| 金币纸签 | `live.economy.currency` | 动态文字；绝不能显示 pending 候选金币冒充到账 |
| 天数纸签 | `live.gameFlow.day` | 显示天数，不据此切换昼夜背景 |
| 炼药锅 | 已拥有设备与选定设备；进入操作前查当前订单 | 当前没有买新锅功能，不能用装饰点击模拟购买 |
| 结束当天 | `model.Action("NextDay")` | 禁止时提供原因，不只是变灰 |
| 商船/档案柜/升级 | 缺少完整业务接入 | 可以预留构图；当前不制造“已开店/可购买/有新线索”的真实状态 |

`bottleQueue` 当前保留收到的信件实例，不是“只包含未开瓶”的队列；不能用它的总长度直接当未读数。模型没有持久的瓶子海面坐标、homeSelectedLetter 或主页动画进度字段，这些可以是 UI 状态，不能擅自加入存档 schema。

真正“进入游戏”先取决于存档：新档显示初始状态；旧档恢复现有信件；有 pending 的旧档应明确引导恢复待确认结果，不能一律展示无事发生的新开主页。

## 9. 一个最小调用示例

以下供现有引擎初始化完成后的页面使用，session/content 由入口传入。它只示范收取→读取→获得显示数据，不自动剪词或替玩家作决定。

```lua
local function receiveAndRead(session, content, letterId, enabled)
    local model = require("ui.PlayModel").New(session, content, enabled)
    local gate = model.Action("ReceiveLetter")
    if not gate.enabled then return nil, gate.message end

    local received = model.Receive(letterId)
    if not received.ok then return nil, model.message end

    local opened = model.Read(received.value.letterInstanceId)
    if not opened.ok then return nil, model.message end

    local view = session.modules.letters.GetView(model.selectedLetter)
    if not view.ok then return nil, view.error.message end
    return {model = model, letter = view.value}, nil
end
```

正式游戏可以把收瓶和开瓶拆成两个玩家动作，分别调用 Receive 与 Read。此例合在一起仅为说明返回值衔接。正式页面不要每个点击都重复 New；保留一个 model，否则会丢失临时选料。

## 10. 尚未实现或尚未冻结的能力

- `Shop` / `ClaimAttachment` 只有拒绝入口，正常返回 NOT_IMPLEMENTED；订单锁定期间可能先返回 ORDER_LOCKED。
- 完整商店、升级购买、信件档案检索/手动关联、配方发现记录、案件、身份、最终愿望与结局不在本版可接接口内。
- 主线复杂出现条件、收取时选正文变体、独立署名和心愿强调的持久字段，见[候选契约](新稿阅读与收取变体_程序交接契约.md)，不是现行 API。
- 当前 PlayModel.Edit 没有特殊物品添加入口；不能把槽位存在理解为功能齐备。
- 拖网、纸张缺口绘制、正文内触摸命中、物件动画与正式美术需要前端实现。逻辑存在不等于这些交互已完成。
- 本地测试与历史桌面取证不等于手机、官方环境或全部 A1～A19 验收。

## 11. 接入验收与维护

按[开发计划 A1～A19](../docs/寄往人间_开发计划与验收标准.md)和[B6 验收记录](B6_窗口与退出恢复验收.md)检查：

1. 新档、已有信件、pending 恢复三种入口状态正确。
2. 收取、已读、剪词重复操作不新增物品；剪后缺口与来源卡一致。
3. 主/辅词选择使用 tokenId；同卡不能占多个位置；同名不同来源仍可区分。
4. 字面失败能观察药效；合规 Preview 展示保存的后续与星级。
5. 确认只结算一次；重置保留前置剪词；切页/动画不绕过门禁。
6. 保存失败和结果不确定分开处理，后者用同槽恢复。
7. 长信、中文、安全区、拖拽/滚动冲突在真实窗口和手机检查。
8. UI 替换后可运行现有 `python -X utf8 -B scripts/debug/run_b6.py` 验证业务回归；旧控件适配器测试不替代新页面触控/渲染验收。

本手册本轮验证：接口与字段静态核对；实际测试结果见[行动记录](../docs/actions/2026-10-05-frontend-handbook-home-prototype.md)。接口变更时同步更新本手册、调用方与相应用例，并更新基线；历史 B0/B5 文档不能覆盖新版本事实。
