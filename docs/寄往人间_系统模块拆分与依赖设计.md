# 《寄往人间》系统模块拆分与依赖设计
## ——高独立、低耦合、便于复用与增删改

> 文档定位：开发架构草案  
> 目标：把《寄往人间》拆成职责清晰、彼此独立的模块，便于比赛开发、后续迭代、内容扩展和功能删减。  
> 核心原则：**内容配置与逻辑分离；模块之间尽量通过事件通信；任何剧情都不要直接写死在核心系统中。**

---

# 一、总体架构原则

## 1.1 玩家始终留在魔药铺

玩家不会主动前往：

- 灰港；
- 仓库；
- 教堂；
- 档案馆；
- 嫌疑人住所；
- 其他人间地点。

玩家与人间的全部交互都通过：

- 漂流瓶；
- 信件；
- 信中附件；
- 后续来信；
- 特殊物品；
- 魔药发货；
- 信件档案桌。

因此：

**炼药不是支线玩法，而是玩家影响人间、推进剧情、获得新信息的唯一核心手段之一。**

---

## 1.2 模块之间尽量不直接写死关系

例如：

错误：

```text
PotionSystem
→ 直接修改托马斯剧情
→ 直接给埃德蒙身份加分
→ 直接解锁成就
```

推荐：

```text
PotionDelivered
→ WorldState 监听
→ Narrative 监听
→ Identity 监听
→ Achievement 监听
```

每个模块只关心自己职责内的数据。

---

## 1.3 内容全部配置化

例如一封信不应该写成：

```text
if day == 4:
    showLetter("TOMAS_02")
```

而应该配置为：

```text
Letter_ID: TOMAS_02
Sender: TOMAS
Address: ORPHANAGE_EAST_WING
Type: MainStory

AppearCondition:
    Day >= 4
    TOMAS_01 completed
    Tomas.fear <= 40

Attachment:
    None

OnComplete:
    TriggerEvent = TOMAS_REPORT_POLICE
```

这样：

- 改出现时间，不改系统；
- 改人物，不改系统；
- 改触发条件，不改系统；
- 删除整条支线，也不影响底层结构。

# 二、推荐拆分为 14 个主要模块

---

# ① Content 内容数据模块

## 职责

统一存储和读取所有静态配置。

包括：

- NPC；
- 信件；
- 地址；
- 词条；
- 材料；
- 配方；
- 商品；
- 店铺升级；
- 案件证据；
- 剧情事件；
- 成就；
- 身份规则；
- 结局配置。

## 输入

配置文件 / ScriptableObject / JSON / CSV / 数据表。

## 输出

供其他模块查询的数据对象。

## 不负责

- 不推进剧情；
- 不修改玩家状态；
- 不计算药效；
- 不判定结局。

## 推荐数据对象

```text
NpcData
LetterData
AddressData
WordTokenData
IngredientData
RecipeData
ShopItemData
UpgradeData
CaseClueData
NarrativeEventData
AchievementData
IdentityRuleData
EndingData
```

---

# ② GameFlow 游戏流程模块

## 职责

负责：

- 当前天数；
- 当前时间段；
- 每日开始；
- 每日结束；
- 主线阶段；
- 是否进入特殊剧情阶段；
- 是否允许打捞；
- 是否允许结算。

## 输入

- 玩家结束当天；
- 剧情事件；
- 存档读取。

## 输出事件

```text
DayStarted
DayEnded
PhaseChanged
MainStoryStageChanged
```

## 不负责

- 不决定今天出现哪封信；
- 不处理具体NPC；
- 不直接解锁剧情内容。

---

# ③ Letter 漂流瓶与信件模块

## 职责

负责：

- 漂流瓶生成；
- 漂流瓶队列；
- 新信件展示；
- 读信；
- 信件附件；
- 主线瓶 / 普通瓶 / 特殊旧瓶；
- 人物后续信；
- 信件状态。

## 信件状态示例

```text
UNRECEIVED
RECEIVED
READ
ORDER_ACCEPTED
ORDER_COMPLETED
FOLLOWUP_AVAILABLE
ARCHIVED
```

## 输入

Narrative 提供“可出现信件”。

## 输出事件

```text
BottleReceived
LetterOpened
LetterRead
AttachmentObtained
LetterArchived
```

## 不负责

- 不判断信件是否重要；
- 不判断案件真相；
- 不决定玩家身份。

---

# ④ Archive 信件档案桌模块

## 职责

整理玩家已经收到的信息。

包括：

- 人物；
- 来信；
- 地址；
- 附件；
- 后续；
- 事件；
- 线索；
- 玩家手动关联。

## 玩家可进行

- 查看同一人物所有来信；
- 对比不同来信中的地址；
- 标记重复地点；
- 把附件和事件关联；
- 查看事件时间线；
- 标记“可能有关联”。

## 关键限制

档案桌不能：

- 主动向NPC发问；
- 远程调查；
- 自动获得未收到的证据；
- 读取人间档案馆。

它只是：

> **整理已经漂到魔药铺里的信息。**

## 输出事件

```text
ArchiveLinkCreated
AddressRelationFound
CluePatternCompleted
CaseInferenceUnlocked
```

---

# ⑤ WordToken 词条模块

## 职责

负责：

- 信件中哪些词可裁剪；
- 裁剪操作；
- 词条库存；
- 词条类型；
- 词条是否已使用；
- 词条保存；
- 特殊不可裁剪词；
- 无名者结局拼贴词池。

## 数据示例

```text
WordToken:
    id
    displayText
    category
    sourceLetter
    sourceNpc
    tags
    reusable
```

## 输出事件

```text
WordCut
WordStored
WordConsumed
WordCategoryCollected
```

## 不负责

- 不计算魔药最终效果。

---

# ⑥ Potion 魔药制作模块

## 职责

根据：

- 主词条；
- 辅助词条；
- 魔药原料；
- 特殊物品；
- 设备等级；

计算：

- 核心效果；
- 强度；
- 持续时间；
- 生效速度；
- 副作用；
- 稳定性。

## 输出对象

```text
PotionResult:
    effects[]
    duration
    intensity
    sideEffects[]
    stability
```

## 输出事件

```text
PotionCreated
PotionFailed
PotionDelivered
```

## 不负责

- 不决定NPC会因此做什么；
- 不判断订单是否符合要求。

---

# ⑦ Order 订单判定模块

## 职责

判断玩家制作的魔药是否满足：

**寄信人的字面要求。**

## 输入

- OrderRequirement；
- PotionResult。

## 输出

```text
CanShip
CannotShip
RequirementMatched
```

## 特别原则

订单系统不判断：

- 是否道德；
- 是否安全；
- 是否符合寄信人真正想要的结果；
- 是否伤害第三方。

只判断：

> **字面上是否完成。**

负责：

- 货币；
- 材料数量；
- 特殊物品；
- 消耗品；
- 奖励结算；

# ⑨ Shop 商店与升级模块

## 职责

负责：

- 商品展示；
- 购买；
- 店铺升级；
- 设备升级；
- 打捞设备；
- 生活设施；
- 特殊商品；
- 人间旅行票。

## 商品分类

### A. 魔药设备

- 炼药锅；
- 炉具；
- 原料柜；
- 词条保存夹；
- 玻璃瓶架。

### B. 打捞设备

- 打捞网；
- 提灯；
- 潮汐仪；
- 漂流瓶暂存架。

### C. 店铺生活设施

- 屋顶；
- 壁炉；
- 窗帘；
- 床铺；
- 温室；
- 书架；
- 门牌。

### D. 特殊商品

- 人间单程旅行票；
- 稀有配方；
- 旧地图；
- 神秘物件。

## 设计原则

商店只广播：

```text
ShopUpgradePurchased
```

“玩家是否持续投资长期居住设施”。

不要写成：

```text
购买温室 → home + 10
```

# ⑩ WorldState 世界状态模块

## 职责

保存当前人间状态。

例如：

```text
Tomas.fear
Mara.hasLandDocument
Lucien.transportRecordExists
Clara.suspicion
Clinic.exposed
Witness.alive
Evidence.reportLetterExists
```

## 输入

- 魔药结果；
- 剧情事件；
- 玩家选择；
- 特殊订单结果。

## 输出事件

```text
NpcStateChanged
EvidenceStateChanged
LocationStateChanged
WorldFlagChanged
```

## 不负责

- 不写剧情台词；
- 不判断最终结局。

# ⑪ Narrative 剧情与事件模块

## 职责

根据：

- 世界状态；
- 天数；
- 玩家订单；
- 人物状态；
- 已读信件；
- 案件阶段；

决定：

- 哪封后续信可以出现；
- 哪个特殊瓶出现；
- 冲突订单何时出现；
- 哪个剧情节点触发；
- 某人物是否继续寄信。

## 输入

各种事件：

```text
PotionDelivered
NpcStateChanged
DayStarted
LetterRead
CaseInferenceUnlocked
```

## 输出

```text
UnlockLetter
UnlockEvent
TriggerConflictBottle
UnlockIdentityGate
```

## 核心原则

**剧情通过条件驱动，不通过硬编码时间线强制播放。**

---

# ⑫ Case 案件与线索模块

## 职责

负责：

- 案件证据；
- 推断；
- 嫌疑人；
- 指认；
- 案件结局；
- 证据完整度。

## 关键概念

案件真凶固定。

但：

- 证据可能消失；
- 证人可能沉默；
- NPC可能逃跑；
- 玩家可能帮助真凶；
- 玩家可能错误指认。

## 输出事件

```text
ClueUnlocked
InferenceUnlocked
SuspectUpdated
AccusationSubmitted
CaseEndingResolved
```

## 不负责

- 不决定玩家是谁。

---

# ⑬ Identity 身份与结局模块

## 五类身份

- 埃德蒙｜真相
- 学徒｜归属
- 旅人｜自由
- 未抵达者｜被看见
- 无名者｜存在

## 判定结构

```text
倾向值
+
身份证据
+
身份确认事件 Gate
```

## 输入

- 玩家长期行为；
- 店铺投资；
- 经济习惯；
- 档案桌推断；
- 普通信件阅读；
- 关键剧情事件；
- 词条收藏。

## 输出

```text
IdentityCandidateChanged
IdentityGateUnlocked
IdentityConfirmed
FinalWishUnlocked
```

## 不负责

- 不判断谁是凶手；
- 不直接决定案件结局。

# 三、核心模块依赖关系

推荐依赖：

```text
Content
  ↓
Letter
  ↓
WordToken
  ↓
Potion
  ↓
Order
  ↓
WorldState
  ↓
Narrative
  ↓
Letter
```

这是最核心闭环。

旁路模块：

```text
Economy ──→ Shop
   │
   └────→ Order Reward

Archive ← Letter / Attachment
Archive ──→ Case
Archive ──→ Identity

Case ← Narrative / Archive / WorldState
Identity ← Narrative / Archive / Shop / Economy / WordToken

Meta ← 全局事件监听
```

# 五、建议的最小开发闭环

比赛开发不要一开始实现全部模块。

第一阶段只做：

```text
Content
↓
Letter
↓
WordToken
↓
Potion
↓
Order
↓
WorldState
↓
Narrative
↓
Letter
```

做出：

1. NPC 寄来第一封信；
2. 玩家阅读；
3. 剪下一个词；
4. 加入辅料；
5. 制作魔药；
6. 系统判断符合订单；
7. 发货；
8. NPC 状态变化；
9. 第二封后续信漂来。

只要这个闭环成立，

**《寄往人间》的核心玩法就成立。**

# 八、模块删减策略

如果比赛时间不足，可以：

## 可直接砍

- 复杂店铺装修；
- 大量成就；
- Endless Mode；
- 部分隐藏身份；
- 高级地址可视化；
- 大量随机普通订单。

## 尽量不要砍

- 信件；
- 剪词；
- 魔药；
- 订单字面判定；
- 人物后续；
- 世界状态变化；
- 至少一个案件闭环；
- 至少两个身份结局。

# 十、当前架构的核心优势

1. **换剧情不改底层系统。**
2. **新增NPC只加配置。**
3. **新增结局不会影响魔药系统。**
4. **删除商店升级也不会破坏案件。**
5. **案件和身份彼此独立。**
6. **玩家永远留在魔药铺，玩法统一。**
7. **所有调查都通过信件和炼药后果自然发生。**
8. **适合比赛期间分阶段开发。**

# 十一、下一步最值得做

建议后续直接进入：

**MVP 原型设计**

只做：

- 1 个 NPC；
- 2 封信；
- 5～8 个可裁剪词；
- 3～5 种材料；
- 2～3 个魔药结果；
- 1 个后续状态变化；
- 1 个最简档案桌。

验证：

> “读信 → 剪词 → 炼药 → 发货 → 世界变化 → 后续信件”

这个循环是否真的好玩。
