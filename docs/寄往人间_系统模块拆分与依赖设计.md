# 一、总体架构原则

## 1.1 玩家始终留在魔药铺

玩家不会主动前往：

- 灰港；
- 仓库；
- 教堂；
- 档案馆；
- 嫌疑人住所；
- 其他人间地点。

玩家与人间的全部交互都通过：

- 漂流瓶；
- 信件；
- 信中附件；
- 后续来信；
- 特殊物品；
- 魔药发货；
- 信件档案桌。

因此：

**炼药不是支线玩法，而是玩家影响人间、推进剧情、获得新信息的唯一核心手段之一。**

---

## 1.2 模块之间尽量不直接写死关系

例如：

错误：

```text
PotionSystem
→ 直接修改托马斯剧情
→ 直接给埃德蒙身份加分
→ 直接解锁成就
```

推荐：

```text
PotionDelivered（仅在玩家确认本单并成功保存后）
→ WorldState 监听
→ Narrative 监听
→ Identity 监听
→ Achievement 监听
```

每个模块只关心自己职责内的数据。

---

## 1.3 内容全部配置化

例如一封信不应该写成：

```text
if day == 4:
    showLetter("TOMAS_02")
```

而应该配置为：

```text
Letter_ID: TOMAS_02
Sender: TOMAS
Address: ORPHANAGE_EAST_WING
Type: MainStory

AppearCondition:
    Day >= 4
    TOMAS_01 completed
    Tomas.fear <= 40

Attachment:
    None

OnComplete:
    TriggerEvent = TOMAS_REPORT_POLICE
```

这样：

- 改出现时间，不改系统；
- 改人物，不改系统；
- 改触发条件，不改系统；
- 删除整条支线，也不影响底层结构。

## 职责

- 地址；
- 附件；
- 后续；
- 事件；

# ⑦ Order 订单判定模块

## 职责

判断玩家制作的魔药是否满足：

**寄信人的字面要求。**

## 输入

- OrderRequirement；
- PotionResult。

要求包含效果标签与阈值，以及信中明确提出的生效、持续、到期残留和禁止效果条件。未明确限制的额外药效不得自动判失败；不符合时列出实际未满足的条件。

## 输出

```text
CanShip
CannotShip
RequirementMatched
```

## 特别原则

订单系统不判断：

- 是否道德；
- 是否安全；
- 是否符合寄信人真正想要的结果；
- 是否伤害第三方。

只判断：

> **字面上是否完成。**

## 本单待确认过程（Order 负责协调）

Order 除字面判定外，依据 Narrative 已解析的直接事件事实、许愿者处境与评分配置计算一至三星和反馈句。三星表示许愿者满意，不是道德分或案件正确性；字面失败不可发货，没有发货后评价。同一订单各星级报酬相同。

星级先存在待确认对象，确认后写入本周目订单记录一次；重置或节点回溯不得沿用被撤销的评价。延迟剧情不追溯改星。学徒考核使用必需订单、分支所选订单和额外已接订单的实际完成记录，未选的成对订单不计入。

沿用现有 14 个模块，由 Order 管理一单的生命周期，调用各模块提供的计算与提交接口；跨模块通知仍使用事件总线。接口查询不等于直接改写其他模块的数据。

```text
进入炼制界面 → 保存本单炼制前基准
→ Potion 计算药效 → Order 检查字面要求
→ 在状态副本上计算药效影响与直接事件
→ Narrative 按事件事实生成直接后续
→ 展示确认 / 重置
   确认：保存整份正式结果，提交一次，再通知监听者
   重置：丢弃副本与待确认文本，返回同一基准重新炼制
```

本单基准在接单、剪词之后，首次投料之前建立，涵盖会被本单改变的库存、词条、订单、世界、信件队列及相关计数。以后每次重试均从同一基准计算，不反复把药效叠到上一次试验状态上。

待确认对象至少保存：本单唯一标识、基准、配方与药效、候选世界状态、直接事件事实、选中片段与最终文本、星级与许愿者反馈、消耗和奖励、确认状态。此为概念对象，具体字段格式在阶段 1 样板中统一。

确认前禁止接下一单、购物、跨天等状态修改；允许阅读本次直接后续、确认或重置。WorldState 与 Narrative 在副本上求值，不能向正式监听者泄露试验事件，也不提前运行多日延迟事件。

确认时保存包含所有本单变化的正式状态；保存失败则保留待确认，不发出完成通知。成功后切换正式状态，依据本单唯一标识防止重复确认，再派发 `PotionDelivered`。监听者不能重新应用已经提交的药效或重复发奖励；事件负载用于通知和刷新。需要影响正式结果的计数应在候选状态中算好，再随本单一起保存。

重置恢复首次投料前的可玩状态，撤销试验消耗、奖励、世界变化与未确认后续，保留此前的剪词和已确认订单。退出重进要恢复待确认对象，不能自动确认、丢失材料或重新随机生成结果。

直接后续可以压缩叙述一段药效过程，但展示文本本身不派发跨天事件。正式时间推进仍由 GameFlow 负责；直接后续不能提前触发需要正式跨天或多单条件的延迟事件。

## 生命周期通知

```text
DeliveryPreviewReady   供界面展示待确认后续
DeliveryReset          供界面返回本单炼制前
PotionDelivered        仅在确认并成功保存后通知正式结果
OrderRatingRecorded    通知已确认星级，不重复结算奖励
```

# ⑪ Narrative 剧情与事件模块

## 职责

根据：

- 世界状态；
- 天数；
- 玩家订单；
- 人物状态；
- 已读信件；
- 案件阶段；

决定：

- 哪封后续信可以出现；
- 哪个特殊瓶出现；
- 冲突订单何时出现；
- 哪个剧情节点触发；
- 某人物是否继续寄信。

## 输入

各种事件：

```text
PotionDelivered
NpcStateChanged
DayStarted
LetterRead
CaseInferenceUnlocked
```

## 输出

```text
UnlockLetter
UnlockEvent
TriggerConflictBottle
UnlockIdentityReveal
```

## 核心原则

**剧情通过条件驱动，不通过硬编码时间线强制播放。**

## 后续事件与文字表达

规则先将药效和人物处境解析成事件事实，例如「睡眠改善」「某项记忆变淡」「证词无法提供」。片段不能反过来创造事实；梦境细节也不能自动成为案件证据。

每个后续可使用两种表达方式：关键事件读取完整定制段落；普通订单用人物口吻模板、基础反馈、额外药效片段和生活后果拼成短文。重要后果即使发生在普通 NPC 身上也使用定制段落。

片段选择顺序：符合事实的关键定制段落 → 专属组合片段 → 人物专属单效果片段 → 通用片段。组合片段覆盖其对应的单效果片段，避免重复；不影响的其他兼容细节仍可保留。互斥组、优先级与稳定的配置编号决定选择顺序，不靠随机抽取故事结果。

一般呈现一个主要生活后果与一至两个细节。多个重要事实同时成立时使用能完整交代它们的定制段落，不因篇幅限制隐藏证据或人物命运的变化。普通感受可以压缩为摘要，但不能写出与事实相反的结论。

片段的触发与排除条件、人物背景、填充值来源、所表达事实均属于内容配置。缺少填充来源时不可展示残留占位符或擅自编造，选择满足条件的通用片段；完全没有覆盖时记录内容错误，不允许生成矛盾文本并进入待确认界面。

本单直接事件在副本上求值并保存，生成待确认直接后续。确认后它进入已确认记录；延迟事件只依据正式世界与 GameFlow 条件继续解锁。

# ⑫ Case 案件与线索模块

## 职责

负责：

- 案件证据；
- 推断；
- 嫌疑人；
- 指认；
- 后期成对瓶子所选订单、药效与未选方后果；
- 案件结局；
- 证据完整度。

## 关键概念

案件真凶固定。

但：

- 证据可能消失；
- 证人可能沉默；
- NPC可能逃跑；
- 玩家可能帮助真凶；
- 玩家可能错误指认。

指认由后期连续成对瓶子的选择、熬药与正式确认来实现，不设置独立的凶手姓名提交菜单。Case 根据世界状态保存归案、逃脱、错抓或未解结果；身份系统只读取此结果。看似帮助警方的反转必须由已知线索与药效解释，不改固定真凶。

Narrative 安排每组出现条件与信件，Order 暂存所选一单，确认后才锁定本组选项并影响未选方；Case 计算案件进展，Meta 保存各分支节点。重置只重新熬当前所选一单，改选另一封走选择前节点回溯。

## 输出事件

```text
ClueUnlocked
InferenceUnlocked
SuspectUpdated
CaseActionResolved
CaseEndingResolved
```

## 不负责

- 不决定玩家是谁。

# ⑬ Identity 身份与结局模块

## 五类身份

- 埃德蒙｜真相
- 学徒｜归属
- 旅人｜自由
- 未抵达者｜被看见
- 无名者｜存在

## 判定结构

```text
有效期内确认购票启程 → 旅人立即结束
其余在身份结算入口：学徒 → 埃德蒙 → 无名者 → 未抵达者
```

学徒条件为固定家居全部购买、当前路线的考核订单覆盖完整且全部三星；不要求归案。埃德蒙要求真凶归案且学徒未达成。未归案、未达学徒时，留存词条达标且无已确认过去则无名者优先，否则未抵达者兜底。不再比较隐藏分或证据百分比。

主线结果确定后允许经营收尾；结束收尾或最终日结束才结算身份。到期主线未完成则记录案件未解。Identity 先锁定一个候选，再由 Narrative 生成相应揭晓，避免互斥特殊瓶同时出现。

埃德蒙自己的信不可剪；未抵达者的埃德蒙对照信可剪，随后必须有玩家自己的旧求助记录；无名者只收到特殊愿望瓶，拼贴「我想……」、预览、确认封瓶后投海，不调用 Potion 或 Order 发货。

## 输入

- 已确认的案件结果；
- 固定家居清单与购买记录；
- 当前分支必需订单 / 所选成对订单 / 额外已接订单的完成与三星记录；
- 正式留存可用词条按定义 ID 去重后的种类数与语义类别；来源副本数量由库存独立维护；
- GameFlow 的终局入口与游戏天数；
- 旅行票确认启程、身份揭晓与最终投瓶事件。

无名者调试门槛为 12 种 / 5 类，同词重复副本不增加种类。最终日、旅行票与固定家居的已接受初值见 [身份规则](寄往人间_五类玩家身份与结局判定规则.md)，由配置提供，不硬编码在 Identity。

## 输出

```text
IdentityCandidateChanged
IdentityRevealUnlocked
IdentityConfirmed
FinalWishUnlocked
```

## 不负责

- 不判断谁是凶手；
- 不直接决定案件结局。

# ⑭ Meta 存档 / 回溯 / 成就模块

## 职责

负责：

- 自动存档；
- 手动存档；
- 剧情节点存档；
- 回溯；
- 成就；
- 周目数据；
- 已解锁结局记录。

保存本单基准与待确认结果，并支持确认失败、重置以及退出重进恢复；这些能力属于阶段 1 核心闭环，不能等到阶段 4 的完整节点回溯才接入。身份计数、证据与完成记录只接受已确认结果，不记录被重置的试验。

后期每组成对选择前、所选订单确认后、剧情分支与案件结果形成时自动建立节点，阶段 3 即接入。完整节点覆盖库存、货币、天数、星级、家居、证据、人物、路线和后续队列；历史展示记录不为当前分支补进度。旅行票启程前、身份揭晓前和最终投瓶前也保存节点。

## 分支节点

在重要事件前自动保存。

例如：

- 冲突漂流瓶；
- 关键魔药发货；
- 成对选择与行动式指认的分支结果；
- 身份确认；
- 最终愿望。

## 输出事件

```text
CheckpointCreated
SaveLoaded
AchievementUnlocked
EndingRecorded
```

# 五、建议的最小开发闭环

比赛开发不要一开始实现全部模块。

先按 [执行计划 B0～B7](../scripts/后端闭环与双人并行开发计划.md) 冻结输入输出，用同一套逻辑完成自动检查和简单界面试玩，再接正式页面。核心模块可并行计算与测试，入口、存档和整单提交由一人集成；接口查询只返回公开结果或状态副本，通知继续使用 EventBus，不暴露可被外部改写的内部表。

第一阶段的玩法主链（另需现有 core、SaveSystem 与 Economy 最小账本支撑）：

```text
Content
↓
Letter
↓
WordToken
↓
Potion
↓
Order
↓
WorldState
↓
Narrative
↓
Letter
```

做出：

1. NPC 寄来第一封信；
2. 玩家阅读；
3. 剪下一个词；
4. 加入辅料；
5. 制作魔药；
6. 系统判断符合订单；
7. 发货，在副本上计算 NPC 状态与直接事件；
8. 展示直接后续，玩家确认或重置回本单炼制前；
9. 确认后保存正式变化与后续记录，继续解锁延迟来信。

这个闭环通过后才有可试玩的核心样板；玩法是否成立还要完成 A1～A19 实机检查，跨订单涌现另按 F3a 验证，不能以接口联通替代体验验收。

# 十、当前架构的核心优势

1. **换剧情不改底层系统。**
2. **新增NPC只加配置。**
3. **新增结局不会影响魔药系统。**
4. **删除商店升级也不会破坏案件。**
5. **案件与身份分别保存，身份只读取明确的案件条件；学徒允许搭配逃脱或未解。**
6. **玩家永远留在魔药铺，玩法统一。**
7. **所有调查都通过信件和炼药后果自然发生。**
8. **适合比赛期间分阶段开发。**
