# 一、范围界定

## 1.1 本计划要交付的

一个可完整通关的比赛版本，满足设计文档《游戏大纲草稿》第「二十三、比赛版本建议原则」中的六条：

1. 剪词做魔药真的好玩；
2. 玩家能看到自己的魔药影响人物后续；
3. 至少存在一次明显的“两个愿望互相影响”；
4. 主线案件能完整闭环；
5. 玩家身份与最终愿望有一次回收；
6. 至少提供数个明显不同的结局。

## 1.2 明确不做的（本计划范围外）

- 不做外出探索、地图移动、主动调查：玩家全程留在魔药铺；
- 不做复杂经营数值树、装修自由摆放；
- 不做联机、排行榜、云存档（单机本地存档即可）；
- 不做实时战斗、3D 场景漫游（本项目是 2D 卡片与文本界面）；
- 不做多周目继承与 Endless Mode（除学徒完整结局作为可选解锁项）。

以上任何一项如果要加，需先修改本文档并重新确认排期。

## 1.3 平台与交付形式

**目标平台：移动端（竖屏）优先，PC 窗口作为开发期验证环境。**

理由：

1. 交付物通过 TapTap 发布，玩家主要在手机上玩。引擎的 UI 库原生带 TapTap 胶囊避让（`SafeAreaView` 的 `nativeMenuInset`），说明移动端本就是首要目标，不是需要额外适配的附加项。
2. 本作核心交互是「读信」。竖屏更接近真实读信姿态，长文本的阅读与滚动也更自然；档案桌的对照在竖屏下用分组卡片实现，不需要横向大画布。
3. `urhox-libs/UI` 的缩放默认是 `DPR_DENSITY_ADAPTIVE`，会按屏幕密度与 DPR 自动适配，移动端不需要额外的适配代码。

具体约定：

- **设计分辨率 1080 × 1920（竖屏）**，NanoVG 采用「模式 A：设计分辨率 + 设计缩放」，参考 `.claude/skills/nvg-resolution-mode/SKILL.md`；
- UI 用 Yoga Flexbox 百分比布局自适应，**不做绝对坐标硬编码**；
- 所有界面最外层套 `SafeAreaView`，避免刘海与胶囊遮挡；
- 开发期在本地预览窗口用自定义竖屏尺寸（如 540×960）验证比例，最终以手机实机为准。

> **注意**：项目屏幕方向在**首次生成测试二维码时写入，之后不可修改**（见 `generate_test_qrcode` 的工具说明）。所以方向必须在首次生成二维码之前定下来。本计划按竖屏推进。

## 1.4 内容量目标与单周目时长

**内容量由玩法需要决定，不由工期倒推。** 先定目标时长与内容规模，再看工期能否承载（见 1.7）。

内容量目标：

| 内容 | 目标量 | 说明 |
|---|---|---|
| 主线信件 | 9 封 | 案件相关人物的来信、后续、附件信 |
| 普通订单 | 20～25 封 | 这是「噪音」功能的密度下限，见下方说明 |
| 后续信 | 20～25 封 | 主线后续完整写，普通订单后续可短（2～4 句） |
| 词条 | 24～30 个 | 覆盖 5～6 类 |
| 辅料 | 6～8 种 | 决定强度 / 持续 / 速度 / 副作用 |
| 商店商品 | 8～12 项 | 三到四类 |
| 身份结局 | 5 类 | 旅人、学徒、埃德蒙、未抵达者、无名者，各有文案；与案件结果分别记录 |

单周目时长推算（耗时按实机估计，未实测，需在阶段 1 用真实数据校准）：

| 内容 | 数量 | 单次耗时 | 小计 |
|---|---|---|---|
| 主线信件（含线索阅读与复查） | 9 封 | 6～10 分钟 | 54～90 分钟 |
| 普通订单（读信 + 剪词 + 炼药 + 发货 + 看后续） | 22 封 | 3～5 分钟 | 66～110 分钟 |
| 档案桌整理与推断 | — | — | 10～20 分钟 |
| 商店与经济决策 | — | — | 5～10 分钟 |
| 案件指认与结局 | — | — | 5～10 分钟 |
| **合计** | | | **约 140～240 分钟（2.5～4 小时）** |

**结论：按上表的内容量，单周目约 2.5～4 小时，不存在「压得太短」的问题。** 真正需要警惕的是相反的失误——把普通订单压到 10～15 封会让「噪音」功能失效：玩家能记住每一封信，于是「分不清哪些信息重要」这个核心体验就没有了。普通订单是设计文档第 8.4 节明确要求的功能（制造噪音、让世界不围绕谋杀案存在），不能当冗余内容砍。

## 1.5 魔药系统的效果合成模型

**魔药不写成配方查找表，而是写成规则合成。** 这既是产能问题，也是主题问题。

如果配方是一张表，那么：需要手写的条目数是「词条 × 辅料 × 档位」的乘积，几十条词条就会膨胀成上千条，写不完；而且玩家的「涌现」会退化成「猜表」，与设计文档第 2.1、2.3 节的立意冲突。

推荐的模型：

```text
词条（携带效果标签）       例如 睡觉 → [sleep]、安静 → [calm]、忘记 → [memory]
    ↓
主词条决定效果主轴，辅助词条改变方向或叠加
    ↓
辅料调整强度 / 持续时间 / 生效速度 / 副作用
    ↓
结果 = 规则合成出的魔药效果
```

药效合成需要手写三类配置：**词条标签表**（24～30 条）、**合成规则**（十几条）、**辅料档位表**（6～8 条）。三者组合后可产生大量药效结果，避免逐配方查表；人物行为、组合后果与后续文案仍需要另外配置和验证，不能据此认为全部剧情成本保持线性。

### 槽位上限（已确认的设计约束）

**魔药的投料数量有硬上限，不是想加多少就加多少。** 槽位是这套系统里最重要的平衡手段，它把「效果合成」从「有什么加什么」变成「必须取舍」：

| 槽位 | 基础容量 | 升级后 | 说明 |
|---|---|---|---|
| 主词条 | 1 | 1（固定） | 决定效果主轴，不可增槽 |
| 辅助词条 | 2 | 3～4 | 设备升级可增加，对应设计文档「增加可放入的辅料槽位」 |
| 原料 | 2 | 3 | 设备升级可增加 |
| 特殊物品 | 1 | 1 | 仅当该信件附带物品时可用，不可购买 |

为什么基础原料只有 2 个槽：原料负责调整五个属性（强度、持续时间、生效速度、副作用、稳定性），而基础只有 2 个槽——**玩家无法同时控制全部属性，必须按订单的实际需要取舍**。这正是订单「字面判定」产生玩法深度的地方，也是设备升级值得花钱的理由。

槽位上限带来的三条玩法约束，需要在阶段验收时确认成立：

1. 订单要求的效果标签数**可能超过**基础槽位能表达的范围，此时必须通过升级设备或换用效率更高的词条来解决；
2. 玩家无法用「把手里所有词条都塞进去」的方式通过订单——满了就放不进去，界面上要有明确的剩余槽位提示；
3. 同一份订单用不同槽位分配能得到不同结果，且都能判定为「符合字面要求」（对应 1.4 的「涌现」立意）。

配置上，槽位容量属于**设备配置**而非魔药配置，应放在 `data/` 的设备表中，随设备升级变化。

**订单判定比对明确的药效条件，不查可接受配方清单。** 基础条件为效果标签与最低权重；信件若明确要求生效时间、持续时间、到期残留或禁止效果，也必须配置并检查。未要求的属性不自行加限制，额外药效不自动导致订单失败。例如「睡一晚、明早还能工作」不能仅凭 sleep 标签放行持续到次日下午的魔药。

### 后续文案：定制与模板结合

主线关键后续与重要证据、人物命运变化使用定制段落；普通订单采用「人物口吻与订单基础反馈 + 额外药效片段 + 生活后果」，不为每个配方写独立整封信。先由药效、人物处境与世界条件确定事件事实，再挑选与事实兼容的片段，关键词只负责检索和有来源的填充。

单效果片段可以共用，并为少数值得表现的组合增加专属片段。优先使用匹配事实的关键定制与组合片段，排除互斥文案；组合片段覆盖对应单效果，避免重复。一般每封呈现一个主要后果和一至两个细节，重要状态变化不能因模板篇幅被隐藏。梦境不生成真实证据，遗忘之后不能无条件完整回忆。

模板数量由每单的实际处境决定，不承诺所有 NPC × 所有药效都有专属分支。每个普通订单需有基础反馈、覆盖其可达直接后果的片段、必要的组合片段及通用反馈。规则在新 NPC 上的适用性、片段冲突和跨订单后果仍需验证。

### 本单确认 / 重置（阶段 1 必须实现）

```text
本单炼制前基准 → 炼药 → 字面判定 → 发货
→ 副本上的直接事件与后续 → 确认 / 重置
确认：保存本单结果、结算一次、继续正式时间线
重置：丢弃待确认结果，回到本单炼制前重新配药
```

基准位于接单、剪词之后且首次投料之前。确认前不接下一单、不购物、不推进天数；直接后续不可裁词或领取附件。试验中的材料、词条、货币、NPC 状态、后续队列和相关计数不能泄露到正式结果中。确认后才能正式累计身份与完成进度；重置保留此前剪词和已确认订单。

直接后续只展示本单近期结果，可以压缩叙述当晚与次晨，但不提前结算需要正式跨天或多单触发的延迟事件。退出重进恢复同一待确认结果；确认保存失败时不发奖励或正式事件。重复确认、反复读后续和重置重试都不能刷收入或进度。同一订单、基准与配方不随机换事件结局。

### 一至三星反馈（阶段 1 接入，阶段 3 用于学徒判定）

字面合规决定是否允许发货，许愿者满意度另用一至三星表示，不改变同一订单的报酬。星级由直接事件事实与人物认知配置，不能按道德、配方价格或案件是否正确打分；帮真凶也可能三星。

评价附在直接后续末尾，先待确认，确认后只存一次；重置与分支回溯撤销未保留的星级。学徒检查固定家居清单、当前路线的必需订单覆盖和全部已接订单三星，成对未选订单与不可达分支不计入，不能靠跳过必需订单达成。

### 主线与身份终局（阶段 3 前置实现）

主线后期通过连续成对瓶子和已确认药效改变世界，每组只能完成一封。取消独立的凶手姓名提交菜单，案件结果按行动、人物与证据条件形成；反转需要可回看的药效与线索依据。每个成对选择、剧情分支和案件结果自动存档，可自由回溯已到达节点。

身份独立结算：有效期内确认购票直接旅人；其余在主线经营收尾结束或最终日结束时，按学徒 → 埃德蒙 → 无名者 → 未抵达者判定。学徒不要求归案，埃德蒙要求归案且未达学徒；未归案、未达学徒时词条达标则无名者优先，否则未抵达者兜底。旅行票窗口按游戏天数，正常经营扣除必要材料费用后需保证可购买。

无名者拼贴后封瓶投海，不熬药；未抵达者除了能剪埃德蒙对照信，还需收到自己的完整旧求助记录。具体对象、阈值与演出入口见《五类玩家身份与结局判定规则》。

## 1.6 范围取舍原则

**取舍要区分两条产能线。** 本项目的分工是：队友负责 `scripts/` 代码，你负责 `data/` 文案（见 1.8）。这意味着**文案工时与开发工时是两条互不相通的产能线**——砍掉一部分文案，并不能换来开发时间；砍掉一个功能，也不会让文案写得更快。

所以取舍必须按「这条线是否吃得消」分别判断，而不是笼统地砍总量：

| 类别 | 处理方式 |
|---|---|
| 需要**开发工时**、玩法价值低的项 | **优先砍**：地图可视化、Endless Mode、复杂升级树、高级成就、多人联机 |
| 需要**文案工时**、玩法价值高的项 | **尽量保**：普通订单密度、人物档案、案件线索、后续信 |
| 两条线都要投入、但非承重 | 视当期进度决定：拼贴诗、未抵达者路线、高级档案桌交互 |

明确列为非承重、可以先不做的：档案桌地图可视化、Endless Mode、多周目继承、成就的高级分类。五类身份的基础条件与终局文案、后期成对分支、三星反馈和本单重置属于本轮确认范围，不再把未抵达者或无名者的基础终局列为可选。

**原则：优先保证设计文档《游戏大纲草稿》第「二十三、比赛版本建议原则」的六条。**

## 1.7 排期（第二约束）

**排期是第二约束。** 当内容目标（1.4）与排期冲突时，按 1.6 砍非承重项，不砍核心闭环的内容密度，也不降低验收标准。

时间基线：开发截至 **10.18** 完成，平台 **10.21** 截止。因为审核需要时间、官方建议提前上传，所以 **10.18 代码冻结并上传送审**，10.19～10.21 只做审核期修复。

| 日期 | 阶段 | 出口条件 |
|---|---|---|
| 10.02～10.04 | 阶段 0 工程骨架 | B1～B7 全过 |
| 10.05～10.10 | 阶段 1 核心闭环 MVP | A1～A19 全过 |
| 10.11～10.13 | 阶段 2 经济与档案桌 | C1～C8 全过 |
| 10.14～10.16 | 阶段 3 案件与身份 | D1～D8 全过 |
| 10.17 | 阶段 4 结局与回溯 | E1～E4 全过 |

**另有一条独立于排期的风险**：送审所需的应用图标、截图、简介必须在 10.18 前备齐，否则开发再顺利也上不去。这不属于开发工作，但会卡住上传。

## 1.8 分工

| 角色 | 负责 | 说明 |
|---|---|---|
| 队友 | `scripts/` 全部代码 | 主开发。系统的实现、UI、调试 |
| 你 | `data/` 全部内容 + `docs/` 设计文档 | 文案与设计。信件文案、人物档案、案件线索、词条与标签表、结局文案 |
| 说明 | `data/` 是两人唯一的接口 | 格式在阶段 0 冻结，之后文案只改 `data/`、开发只改 `scripts/`，不互相覆盖 |

**关键前提**：`data/` 的配置格式必须在阶段 0 结束前冻结，否则文案线无法并行开工，只能干等代码。建议阶段 0 结束时产出「一个人物 / 一封信 / 一个词条 / 一个配方 / 一个订单要求」的样板配置作为格式基准。

2026-10-02 的设计需要在原样板之上补充订单的明确属性条件、后续事实与片段条件，以及待确认存档结构。现有 `requirement.tags`、`appearCondition` 与 SaveSystem 尚未提供全部新增能力；本次只更新文档。阶段 1 开工前由代码线与内容线共同补齐样板和填写说明，再更新格式基准，不以「已经冻结」推断新增字段已经可用。

**队友尚未接入期间的安排**：在队友回复前，可先由 AI 搭好阶段 0 的骨架与 `data/` 样板配置，队友接入后直接接手 `scripts/`，不必从头理解工程结构。

# 二、技术底座与工程约定

| 项目 | 采用方案 |

# 三、开发与验收链路

每一阶段都走同一条链路，不做额外流程：

1. **本地实现**：在 `scripts/` 写代码，`data/` 加配置；
2. **本地验证**：`taptap-maker preview run --target-dir "D:\To the Human World"` 在窗口里实际玩一遍，看日志有无报错；
3. **提交构建**：确认无误后说“提交”或“构建”，走 Maker MCP 提交并远端构建；
4. **验收**：按本文档对应阶段的验收标准逐条走查，全部通过才进入下一阶段。

**约定**：每阶段的验收由用户实机走查，不以“代码写完”代替“验收通过”。AI 侧的自测只作为提交前的自检，不作为验收依据。

`screenshots_supported: false`。判断渲染是否正常只能靠布局尺寸自检 + 用户实机看窗口。

## 阶段 1：核心闭环 MVP

### 目标

验证设计文档的核心命题：**读信 → 剪词 → 炼药 → 发货 → 直接后续 → 确认 / 重置 → 正式世界变化与延迟来信** 这个循环是否成立、是否好玩。

### 范围

只做 1 个 NPC、2 封逻辑信件（首信与直接后续，后续可有多个模板版本）、5～8 个可裁剪词、3～5 种材料，至少 3 种可区分的合规药效结果与 1 组组合冲突用例。接入本单基准、待确认存档和确认 / 重置；延迟来信的完整链在后续内容阶段补齐。**不做**商店、档案桌、身份、案件。

### 交付物

- `data/`：该 NPC 的人物配置、两封信的完整配置、词条配置、材料与配方配置
- `systems/Letter.lua`、`systems/WordToken.lua`、`systems/Potion.lua`、`systems/Order.lua`、`systems/WorldState.lua`、`systems/Narrative.lua`
- `ui/`：打捞界面、读信与剪词界面、炼药界面
- `systems/Narrative.lua` 中的条件驱动信件解锁逻辑
- 本单直接事件、模板与片段样板，以及 Order / SaveSystem 的待确认与恢复能力

### 验收标准

- **A1** 启动后进入主界面，可见海面/打捞区域、当前天数、货币数值。
- **A2** 触发打捞后，至少 1 个漂流瓶进入待处理队列，且内容来自 `data/` 中的配置信件。
- **A3** 打开信件后完整显示三段结构（自我介绍、正文、详细地址）；中文显示正常，无方框、无乱码、无缺字。
- **A4** 信件中可裁剪词不少于 5 个；点击某个词后被剪下，且同时满足三点：原位置留下**可见空缺**、该词条进入词条库存、重新打开该信时空缺仍然存在。
- **A5** 词条库存界面能看到已剪词条，含词条文本与来源信件。
- **A6** 炼药界面能放入 1 个主词条与至少 2 种辅料；炼制后生成魔药结果，结果包含效果名称、强度、持续时间三项。
- **A7** 订单判定给出明确的“符合 / 不符合字面要求”结论；不符合时指出**未满足的具体条件**，而不是只给一句失败提示。
- **A8** 发货后副本中的 NPC 状态发生可观测变化，调试面板区分正式状态与待确认状态；确认后正式状态变化且只应用一次，重置后正式状态保持本单基准。
- **A9** 发货后立即展示第二封逻辑信件的直接后续；文案**引用了第一封信的订单结果**，无需先跨天。确认后归档一次；重置后撤销未确认文本与结果，不重复投进正式打捞队列。
- **A10** 退出游戏后重新进入，天数、词条库存、已剪信件状态、NPC 状态值全部保留。
- **A11** 全流程连续操作 5 分钟无 Lua 报错、无界面卡死、无控件重叠错位。
- **A12** 架构验收：新增第二封首信**只需改 `data/` 配置**、不需改系统代码。以实测验证——加一封配置信，它能按配置条件正常出现。
- **A13** 魔药采用规则合成而非查表（对应 1.5）：同一个主词条搭配不同辅料，能得到**至少 3 种可区分的不同结果**；并且新增一个词条只需在 `data/` 里添加它的效果标签，**不需改合成逻辑代码**。以实测验证。
- **A14** 至少 3 种满足同一订单的组合，因额外药效产生可辨识的直接后续差异；有标签但持续过长、违反明确次晨工作条件的魔药不能发货。判定条件必须展示给玩家。
- **A15** 普通订单后续由事实驱动模板与片段产生；测试单效果、组合专属片段、互斥片段、无专属片段和缺少填充值的情况。无矛盾、重复、残留占位符或凭空证据；未满足字面要求的组合不能通过发货领取后续。
- **A16** 阅读直接后续后点击重置，返回首次投料前；库存、消耗词条、货币、订单、NPC、后续队列和完成计数与基准一致，此前剪词与已确认订单保留。换配方重试不会叠加上次试验药效。
- **A17** 确认仅提交一次，重复点击、重开后续与读档不重复发奖励或修改状态。确认前不允许接单、购物、跨天、剪后续词或领附件；重新采用相同基准与配方得到相同事件事实。
- **A18** 退出重进恢复已保存的待确认结果，仍可确认或重置。模拟确认保存失败：保留待确认、未发正式事件与奖励，重试成功也只提交一次。
- **A19** 同一订单能根据直接事件得到一、二、三星及对应反馈句，最高三星，各等级奖励金额一致；字面不合规仍不可发货。评价先待确认，重置不保留，确认只记录一次，延迟事件不追溯改星。

### 阶段 1 的判定方式

由用户实机走查 A1～A19。其中 A12 与 A13 需要现场改配置验证，不能只看代码。开发前先用 [路人甲纸面验证](寄往人间_魔药后续与重置_纸面验证.md) 检查文案与规则；纸面推演不计入实机通过项。

## 阶段 3：案件与身份

### 目标

让主线通过连续成对瓶子的行动式指认形成不同案件结果，五类身份按具体达成条件与优先级结算，分别保存两条结局轴。

### 交付物

- `systems/Case.lua`、`systems/Identity.lua`、`ui/CaseScreen.lua`
- `data/`：案件证据、嫌疑人、成对组与后果、评分规则、五类身份具体条件、终局揭晓与文案配置
- 调试面板扩充：案件结果、成对选择、家居 / 三星覆盖、旅行票窗口、词条阈值与当前候选
- 每个已到达剧情分支的节点存档与回溯；无名者拼贴、预览、封瓶和投海流程

### 验收标准

- **D1** 至少 3 条案件线索通过信件或附件抵达，并能在案件界面中查看。
- **D2** 主线后期连续成对瓶子每组只能确认一封，所选配方的不同药效会影响结果，未选方按配置产生后果；能形成归案、逃脱、错抓、未解等案件结果。不存在独立的凶手姓名提交菜单，至少一处反转可以从已有线索与药效解释。
- **D3** 按具体条件与优先级判定：学徒和归案同时满足只触发学徒；未达学徒但归案触发埃德蒙；未归案、未达学徒时，词条数量与类别达标**且当前分支尚未确认个人过去**才触发无名者，否则未抵达者兜底。无隐藏分参与资格判定。
- **D4** 调试面板显示正式案件结果、每组成对选择、固定家居完成度、必需订单 / 所选分支 / 额外已接订单的三星覆盖、票有效期、词条数量与类别、终局入口与候选。能区分正式进度和待确认结果。
- **D5** 五类身份资格与揭晓流程均可达；埃德蒙自己的信不可剪，未抵达者的埃德蒙对照信可剪且有玩家自己的完整旧记录；无名者不出现埃德蒙瓶，直接进入特殊愿望瓶。
- **D6** 覆盖学徒 + 归案、学徒 + 逃脱、学徒 + 未解等组合；案件失败不剥夺学徒。主线先结算，经营收尾结束或最终日结束才选择身份；终局无候选空档，无重复特殊瓶。
- **D7** 负向验收：跳过必需订单、仅完成少量三星、未选成对订单、跨分支历史最佳评价均不能伪造学徒达成；少一件家居、少一枚或少一类词条的边界按配置落到正确路线。例外仅为有效期内主动购票立即结束。
- **D8** 回归验收：阶段 1、2 的验收项仍然全部通过；被重置的试验不得累计身份、证据或完成记录，确认后只累计一次。
- **D9** 旅行票显示有效期与剩余天数，最后有效日可购、下一天停售；取消不扣款，确认时复查并一次扣款结束。购票前有节点存档；保存失败和读档不重复扣款。正常经营扣除必要材料费用后可在窗口内支付票价。
- **D10** 每组成对选择前、确认后、剧情分支与案件结果有节点存档；恢复后同步还原天数、资金、库存、星级、家居、证据、人物与后续队列，可改选另一封。本单重置仅重新熬当前所选一单，不能完成两封。节点列表不提前展示未探索结局。

- 最终愿望界面（含无名者的拼贴诗交互）

### 验收标准

- **E1** 五类身份均有可辨识的结局文案与呈现，案件结果另段展示并独立保存；旅人可提前结束，未完成主线记未解。埃德蒙所有文案变体均以真凶归案为前提。
- **E2** 阶段 3 的成对节点完整保留；购票启程前、身份揭晓前、无名者最终封瓶前也自动建立存档点。
- **E3** 从任意存档点回溯后，可以重新做出不同选择并抵达不同结局，且**无需重玩此前的经营内容**。
- **E4** 成就可解锁，重启后保留。
- **E5** 已解锁结局在元数据中记录，可在界面查看。
- **E6** 无名者使用正式留存词条拼贴预印的「我想……」，至少一个词、可预览修改，确认封瓶并投海后播放结局且保留原句；不调用炼药或普通发货。移动词条不刷库存，也不因进入拼贴导致资格被撤销。
- **E7** 回归验收：阶段 1～3 的验收项仍然全部通过。

## 阶段 5：内容填充与打磨

### 目标

把内容量补齐到比赛版本该有的样子，并消除体验瑕疵。

### 验收标准

- **F1** 一周目可以完整通关，无阻断性 bug（不会卡死、不会无法继续、不会丢档）。
- **F2** 正常游玩中必然可遇见至少 1 处“两个愿望互相影响”。
- **F3** 至少 1 条“玩家的魔药导致人物行为改变、并因此产生新来信”的因果链清晰可感（玩家能意识到是自己造成的）。
- **F3a** 至少一处已确认订单的额外药效影响另一个订单或人物后续，玩家能从来信中辨认因果；不以“不同配方生成不同文字”代替跨订单状态变化。
- **F4** 中文文本在目标分辨率下无溢出、无异常断行、无字体缺失；长信滚动正常。
- **F5** 首次进入时有必要的玩法引导（如何打捞、如何剪词、如何炼药），不需要玩家看外部说明。
- **F6** 连续游玩 20 分钟无因内存持续增长导致的卡顿或崩溃。

# 五、终验标准

全部阶段完成后，按设计文档《游戏大纲草稿》第「二十三、比赛版本建议原则」的六条终验：

1. 剪词做魔药在实机试玩中被评价为“好玩”，而不是“操作繁琐”；
2. 玩家确实能看到自己的魔药影响人物后续；
3. 至少存在一次明显的“两个愿望互相影响”；
4. 主线案件能通过后期成对瓶子的行动式指认完整闭环；
5. 玩家身份与最终愿望有一次回收；
6. 五类身份基础结局可达，案件与身份分开记录，至少验证学徒与逃脱 / 未解组合。

终验由用户实机走查完成，不以自动化检查代替。

# 六、风险与对策

| 风险 | 说明 | 对策 |
|---|---|---|
| 内容产能不足 | 文案量（信件、人物、案件线索）由文案线独立承担，写作速度与开发进度无关 | 内容目标按 1.4 定；出现缺口时按 1.6 砍开发侧非承重功能，或缩短普通订单后续信的长度，**不砍普通订单的数量** |
| 魔药配置膨胀 | 若把配方写成查表，条目数会随「词条 × 辅料 × 档位」乘积增长，最终写不完 | 采用 1.5 的效果合成与条件判定，不为每个订单预写可接受配方；剧情组合与模板覆盖另外验证，不承诺总文案量线性 |
| 模板文案冲突 | 多药效片段可能相互矛盾，或只换词却没有事件差异 | 先判事实，再按条件、互斥组和优先级选片段；重要组合定制，用 A14～A15 验证 |
| 重置污染正式状态 | 试验重复发奖、遗留人物状态或刷身份进度 | 阶段 1 接入本单基准与待确认结果；A16～A18 检查恢复、一次提交与退出重进 |
| 两人协作冲突 | 文案与开发同时改同一批文件会互相覆盖 | `data/` 是唯一接口，格式在阶段 0 冻结；之后文案只改 `data/` 与 `docs/`，开发只改 `scripts/` |
| 剪词交互实现风险 | 引擎的 `RichText` 支持可点击片段，但「剪后留空缺 + 长信滚动 + 多处词条命中」需要实机验证 | 阶段 1 先用短信验证命中与重绘，再上长信；必要时限制单屏可剪词数量 |
| 事件总线过度设计 | 为了解耦引入异步或复杂调度，反而难以调试 | 只做「注册 / 派发 / 优先级」最小实现，同帧同步派发 |
| 中文排版 | 长段落换行、标点挤压、字体回退可能出问题 | 阶段 1 就锁定目标分辨率做排版走查，不拖到打磨阶段 |
| 存档结构变更 | 开发中存档结构必然变化，容易读旧档崩溃 | SaveSystem 带结构版本号，读取失败回落默认值（阶段 0 的 B3 已覆盖） |
| 玩法验证滞后 | 一直堆内容，到最后才发现闭环不好玩 | 阶段 1 就是玩法验证关卡，闭环不好玩则回到设计层调整，不继续加内容 |
| 送审素材缺失 | 图标、截图、简介不齐会直接卡住上传，与开发进度无关 | 提前列入待办（见七），10.18 前必须备齐 |
