# 《寄往人间》开发计划与验收标准

> 文档定位：Maker 工程（UrhoX / Lua）的实施计划
> 目标：把四份设计文档落成可执行、可验收的开发顺序
> 前提：工程已绑定 Maker 项目「寄往人间」（app_id `76909fb8-3dc3-4adc-8c49-fe56bab4393e`）
> 原则：**先跑通闭环，再堆内容；每个阶段有可判定的验收标准，未通过不进入下一阶段。**

---

# 一、范围界定

## 1.1 本计划要交付的

一个可完整通关的比赛版本，满足设计文档《游戏大纲草稿》第「二十三、比赛版本建议原则」中的六条：

1. 剪词做魔药真的好玩；
2. 玩家能看到自己的魔药影响人物后续；
3. 至少存在一次明显的“两个愿望互相影响”；
4. 主线案件能完整闭环；
5. 玩家身份与最终愿望有一次回收；
6. 至少提供数个明显不同的结局。

## 1.2 明确不做的（本计划范围外）

- 不做外出探索、地图移动、主动调查：玩家全程留在魔药铺；
- 不做复杂经营数值树、装修自由摆放；
- 不做联机、排行榜、云存档（单机本地存档即可）；
- 不做实时战斗、3D 场景漫游（本项目是 2D 卡片与文本界面）；
- 不做多周目继承与 Endless Mode（除学徒完整结局作为可选解锁项）。

以上任何一项如果要加，需先修改本文档并重新确认排期。

## 1.3 平台与交付形式

**目标平台：移动端（竖屏）优先，PC 窗口作为开发期验证环境。**

理由：

1. 交付物通过 TapTap 发布，玩家主要在手机上玩。引擎的 UI 库原生带 TapTap 胶囊避让（`SafeAreaView` 的 `nativeMenuInset`），说明移动端本就是首要目标，不是需要额外适配的附加项。
2. 本作核心交互是「读信」。竖屏更接近真实读信姿态，长文本的阅读与滚动也更自然；档案桌的对照在竖屏下用分组卡片实现，不需要横向大画布。
3. `urhox-libs/UI` 的缩放默认是 `DPR_DENSITY_ADAPTIVE`，会按屏幕密度与 DPR 自动适配，移动端不需要额外的适配代码。

具体约定：

- **设计分辨率 1080 × 1920（竖屏）**，NanoVG 采用「模式 A：设计分辨率 + 设计缩放」，参考 `.claude/skills/nvg-resolution-mode/SKILL.md`；
- UI 用 Yoga Flexbox 百分比布局自适应，**不做绝对坐标硬编码**；
- 所有界面最外层套 `SafeAreaView`，避免刘海与胶囊遮挡；
- 开发期在本地预览窗口用自定义竖屏尺寸（如 540×960）验证比例，最终以手机实机为准。

> **注意**：项目屏幕方向在**首次生成测试二维码时写入，之后不可修改**（见 `generate_test_qrcode` 的工具说明）。所以方向必须在首次生成二维码之前定下来。本计划按竖屏推进。

## 1.5 比赛版本范围裁剪（对照设计文档）

设计文档的完整设想远超 17 天能承载的规模，比赛版本按下表裁剪：

| 项目 | 设计文档 | 比赛版本 | 说明 |
|---|---|---|---|
| 玩家身份 | 5 条路线 | 3 条（埃德蒙 / 学徒 / 旅人）+ 无名者作为拼贴诗隐藏结局 | 未抵达者需要完整档案与大量普通 NPC 内容支撑，本次不做 |
| 主案件 | 完整角色网 | 1 个完整案件，嫌疑人 3～4 人，核心线索 5～6 条 | 案件必须能闭环，但不必穷尽支线 |
| 信件 | 大量普通订单 + 主线 | 主线 8～10 封 + 普通订单 10～15 封 | 普通订单是经济来源与「噪音」，但要控量 |
| 词条 | 完整分类体系 | 20～30 个词条，覆盖 5～6 类 | |
| 魔药 | 完整配方体系 | 15～20 种可组合结果 | |
| 商店升级 | 四类完整升级树 | 3 类，每类 2～3 项 | 保留「留下还是离开」的消费表达即可 |
| 档案桌 | 高级地址可视化 | 按人物 / 地址分组 + 手动标记关联 | 不做地图可视化 |
| 成就 | 四类 | 5～8 个 | |
| 结局 | 多维度自由组合 | 4 个（身份 × 案件结局） | |
| 拼贴诗 | 完整语法槽系统 | 简化版：从已保存词条中选词拼接 | 保留主题回收即可 |

**裁剪原则**：优先保证设计文档《游戏大纲草稿》第「二十三、比赛版本建议原则」的六条，其余一律可砍。

## 1.6 两人分工建议

17 天的关键风险不是代码，而是**内容量**。建议这样分：

- **开发主力**负责 `scripts/` 的系统与 UI，按阶段推进，是唯一改代码的人，避免两人同时改同一批文件；
- **内容主力**负责 `data/` 的内容配置：信件文案、人物档案、案件线索、词条与配方数值。

前提是：**`data/` 的配置格式必须在阶段 0 就冻结**，否则内容主力无法并行开工。建议阶段 0 结束时先产出「一个人物 / 一封信 / 一个词条 / 一个配方」的样板配置作为格式基准，之后内容主力照此批量填写。

## 1.7 阶段 1 示范 NPC

按约定使用一位与主线无关的路人甲（暂定名「路人甲」，后续可替换为正式人名）：

- 身份：灰港普通居民，与谋杀案没有直接关系；
- 首信：一个字面清晰、容易用魔药满足的普通愿望；
- 后续信：内容反映玩家所制魔药造成的结果；
- 作用：只验证闭环，不消耗主线内容。

# 三、开发与验收链路

每一阶段都走同一条链路，不做额外流程：

1. **本地实现**：在 `scripts/` 写代码，`data/` 加配置；
2. **本地验证**：`taptap-maker preview run --target-dir "D:\To the Human World"` 在窗口里实际玩一遍，看日志有无报错；
3. **提交构建**：确认无误后说“提交”或“构建”，走 Maker MCP 提交并远端构建；
4. **验收**：按本文档对应阶段的验收标准逐条走查，全部通过才进入下一阶段。

**约定**：每阶段的验收由用户实机走查，不以“代码写完”代替“验收通过”。AI 侧的自测只作为提交前的自检，不作为验收依据。

## 阶段 0：工程骨架

### 目标

建立所有后续模块都要依赖的地基，并在本地预览中跑起来。

### 交付物

- `scripts/main.lua`：入口，基于 `scaffold-2d.lua`
- `scripts/core/EventBus.lua`：事件注册与派发
- `scripts/core/SaveSystem.lua`：存档读写，带结构版本号
- `scripts/core/GameFlow.lua`：天数、时段、主线阶段
- `scripts/debug/DebugPanel.lua`：调试面板

### 验收标准

- **B1** 启动本地预览后出现游戏窗口，渲染出 UI 根控件（屏幕上有可见内容，不是黑屏）。
- **B2** 事件总线完成最小验证：注册两个监听者，派发一个事件，两者都按注册顺序收到并打印。
- **B3** 存档系统能写入并读回一个含嵌套表的存档；读到一个字段缺失或版本号偏旧的存档时**不崩溃**，而是回落到默认值。
- **B4** GameFlow 能推进天数，并在跨天时派发 `DayStarted` / `DayEnded` 事件，调试面板上能看到天数变化。
- **B5** 调试面板可开关；打开后显示当前天数、世界状态表、最近的事件日志。
- **B6** 入口结构来自 `templates/scaffold-2d.lua`，未自行发明入口或强改引擎约定的生命周期。
- **B7** 本地预览连续运行 3 分钟无 Lua 报错；关闭窗口后进程正常退出。

## 阶段 1：核心闭环 MVP

### 目标

验证设计文档的核心命题：**读信 → 剪词 → 炼药 → 发货 → 世界变化 → 后续来信** 这个循环是否成立、是否好玩。

### 范围

只做 1 个 NPC、2 封信、5～8 个可裁剪词、3～5 种材料、2～3 种魔药结果、1 次后续状态变化。**不做**商店、档案桌、身份、案件。

### 交付物

- `data/`：该 NPC 的人物配置、两封信的完整配置、词条配置、材料与配方配置
- `systems/Letter.lua`、`systems/WordToken.lua`、`systems/Potion.lua`、`systems/Order.lua`、`systems/WorldState.lua`、`systems/Narrative.lua`
- `ui/`：打捞界面、读信与剪词界面、炼药界面
- `systems/Narrative.lua` 中的条件驱动信件解锁逻辑

### 验收标准

- **A1** 启动后进入主界面，可见海面/打捞区域、当前天数、货币数值。
- **A2** 触发打捞后，至少 1 个漂流瓶进入待处理队列，且内容来自 `data/` 中的配置信件。
- **A3** 打开信件后完整显示三段结构（自我介绍、正文、详细地址）；中文显示正常，无方框、无乱码、无缺字。
- **A4** 信件中可裁剪词不少于 5 个；点击某个词后被剪下，且同时满足三点：原位置留下**可见空缺**、该词条进入词条库存、重新打开该信时空缺仍然存在。
- **A5** 词条库存界面能看到已剪词条，含词条文本与来源信件。
- **A6** 炼药界面能放入 1 个主词条与至少 2 种辅料；炼制后生成魔药结果，结果包含效果名称、强度、持续时间三项。
- **A7** 订单判定给出明确的“符合 / 不符合字面要求”结论；不符合时指出**未满足的具体条件**，而不是只给一句失败提示。
- **A8** 发货后 NPC 的世界状态值发生可观测变化（例如恐惧值下降），该变化在调试面板中可见。
- **A9** 当世界状态满足配置条件时，第二封后续信进入打捞队列；其文案**引用了第一封信的订单结果**（能看出因果，不是无关的第二封信）。
- **A10** 退出游戏后重新进入，天数、词条库存、已剪信件状态、NPC 状态值全部保留。
- **A11** 全流程连续操作 5 分钟无 Lua 报错、无界面卡死、无控件重叠错位。
- **A12** 架构验收：新增第二封首信**只需改 `data/` 配置**、不需改系统代码。以实测验证——加一封配置信，它能按配置条件正常出现。

### 阶段 1 的判定方式

由用户实机走查 A1～A12。其中 A12 需要现场加一封配置信验证，不能只看代码。

## 阶段 2：经济与档案桌

### 目标

让订单收益有去处，让已收到的信息可以整理，为案件推理做准备。

### 交付物

- `systems/Economy.lua`、`systems/Shop.lua`
- `systems/Archive.lua`、`ui/ArchiveScreen.lua`、存档点（`meta/Checkpoint.lua` 雏形）
- `data/`：商品、升级、材料库存配置

### 验收标准

- **C1** 完成订单结算货币；货币数值在界面上可见，且重启后保留。
- **C2** 商店可购买至少 3 类商品（材料、配方、设备升级）；购买后货币即时扣减、对应能力或库存即时生效。
- **C3** 设备升级对炼药产生可观察影响（例如增加辅料槽位或降低某种副作用），在炼药界面上能看到差异。
- **C4** 材料不足时无法炼制，界面给出明确提示（说明缺什么），而不是静默失败。
- **C5** 档案桌能按人物分组查看其全部来信。
- **C6** 档案桌能对比不同信件中的地址，并支持玩家手动标记“可能有关联”。
- **C7** 负向验收：档案桌中不存在任何获取未收到信息的入口——不能主动发问、不能远程调查、不能解锁未收到的证据。
- **C8** 回归验收：加入经济与档案桌后，阶段 1 的 A1～A11 仍然全部通过。

## 阶段 3：案件与身份

### 目标

让主线悬案成立，让玩家身份通过长期行为“涌现”。

### 交付物

- `systems/Case.lua`、`systems/Identity.lua`、`ui/CaseScreen.lua`
- `data/`：案件证据、嫌疑人、五类身份的证据与 Gate 配置、结局配置
- 调试面板扩充：身份倾向值、证据进度、Gate 状态、当前候选

### 验收标准

- **D1** 至少 3 条案件线索通过信件或附件抵达，并能在案件界面中查看。
- **D2** 玩家可以提交最终指认；指认结果按“是否正确 + 证据是否充分”给出至少 3 种不同反馈。
- **D3** 身份判定按“倾向值 + 身份证据 + 确认 Gate”三层工作；Gate 未完成时，即使倾向值达标也不确认身份（构造测试存档验证）。
- **D4** 调试面板实时显示各路线倾向值、证据收集进度、Gate 状态、当前候选身份。
- **D5** 至少 2 条身份路线可以完整达成（建议埃德蒙与学徒）。
- **D6** 身份判定不是单一最高分：构造两条倾向值接近的测试存档，验证终局时给出叙事选择，而不是直接取最高值。
- **D7** 负向验收：单次偶然行为不改变身份候选（例如只买一件生活装饰、只查一次档案）。
- **D8** 回归验收：阶段 1、2 的验收项仍然全部通过。

---

## 阶段 4：结局与元系统

### 目标

让选择有分量：多结局、可回溯、有成就。

### 交付物

- `meta/Checkpoint.lua`、`meta/Achievement.lua`、`meta/EndingRecord.lua`
- `ui/EndingScreen.lua`
- 最终愿望界面（含无名者的拼贴诗交互）

### 验收标准

- **E1** 至少 4 个不同结局可达成（身份结局与案件结局的组合），每个结局有可辨识的结局呈现。
- **E2** 关键节点自动建立存档点：冲突漂流瓶、关键魔药发货、最终指认、身份确认、最终愿望。
- **E3** 从任意存档点回溯后，可以重新做出不同选择并抵达不同结局，且**无需重玩此前的经营内容**。
- **E4** 成就可解锁，重启后保留。
- **E5** 已解锁结局在元数据中记录，可在界面查看。
- **E6** 无名者路线的拼贴诗交互可以完成：玩家用自己保存的词拼出一句愿望，并得到与之匹配的结局呈现。
- **E7** 回归验收：阶段 1～3 的验收项仍然全部通过。

## 阶段 5：内容填充与打磨

### 目标

把内容量补齐到比赛版本该有的样子，并消除体验瑕疵。

### 验收标准

- **F1** 一周目可以完整通关，无阻断性 bug（不会卡死、不会无法继续、不会丢档）。
- **F2** 正常游玩中必然可遇见至少 1 处“两个愿望互相影响”。
- **F3** 至少 1 条“玩家的魔药导致人物行为改变、并因此产生新来信”的因果链清晰可感（玩家能意识到是自己造成的）。
- **F4** 中文文本在目标分辨率下无溢出、无异常断行、无字体缺失；长信滚动正常。
- **F5** 首次进入时有必要的玩法引导（如何打捞、如何剪词、如何炼药），不需要玩家看外部说明。
- **F6** 连续游玩 20 分钟无因内存持续增长导致的卡顿或崩溃。

# 五、终验标准

全部阶段完成后，按设计文档《游戏大纲草稿》第「二十三、比赛版本建议原则」的六条终验：

1. 剪词做魔药在实机试玩中被评价为“好玩”，而不是“操作繁琐”；
2. 玩家确实能看到自己的魔药影响人物后续；
3. 至少存在一次明显的“两个愿望互相影响”；
4. 主线案件能完整闭环（有明确的指认与结果）；
5. 玩家身份与最终愿望有一次回收；
6. 至少提供数个明显不同的结局（≥4 个）。

终验由用户实机走查完成，不以自动化检查代替。

# 六、风险与对策

| 风险 | 说明 | 对策 |
|---|---|---|
| 内容量失控 | 设计文档体量为 5 类身份、14 个模块、完整谋杀案，远超比赛版本可承载的规模 | 按阶段卡验收；阶段 1 未通过不进入内容扩张；阶段 5 按剩余时间裁剪 |
| 剪词交互实现风险 | 引擎的 `RichText` 支持可点击片段，但“剪后留空缺 + 长信滚动 + 多处词条命中”需要实机验证 | 阶段 1 先用短信验证命中与重绘，再上长信；必要时限制单屏可剪词数量 |
| 事件总线过度设计 | 为了解耦引入异步或复杂调度，反而难以调试 | 只做“注册 / 派发 / 优先级”最小实现，同帧同步派发 |
| 中文排版 | 长段落换行、标点挤压、字体回退可能出问题 | 阶段 1 就锁定目标分辨率做排版走查，不拖到打磨阶段 |
| 存档结构变更 | 开发中存档结构必然变化，容易读旧档崩溃 | SaveSystem 带结构版本号，读取失败回落默认值（阶段 0 的 B3 已覆盖） |
| 远端构建依赖 | 服务端代码改动需提交构建后才生效 | 本项目为单机，无服务端代码；日常验证走本地预览，减少远端构建次数 |
| 玩法验证滞后 | 一直堆内容，到最后才发现闭环不好玩 | 阶段 1 就是玩法验证关卡，闭环不好玩则回到设计层调整，不继续加内容 |
