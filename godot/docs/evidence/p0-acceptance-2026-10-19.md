## 问题清单

### P0-01：宽屏主页仍有生硬侧栏，宽屏视觉要求未完成

- 位置：`src/presentation/home_scene.gd:50-54,73-91`。
- 复现：运行当前 Windows EXE，以 1600×720 显示主页。
- 结果：1920×1080 房间等比居中，两侧各约 160 屏幕像素被深褐色底和纵向拉伸的木牌覆盖；顶部与底部仍有大片接近纯色的区域，场景边界明显。不是自然扩展或柔和延展的海港/室内画面。
- 依据：P0 要求超宽屏通过扩展背景/柔和延展处理；方案放行条件要求宽屏不出现生硬黑带。换成深褐色直栏仍保留相同视觉问题。
- 证据：[本轮实际包截图](D:/p0-acceptance-20261019/home-1600x720.png)。截图由该 EXE 自身 viewport 导出，已逐张查看，未使用桌面截屏或输入。
- 处理建议：在保留室内关键物件比例的前提下完成连续背景延展；重新提交 16:9、19.5:9、20:9、2412×1080 的主页证据。若用户决定保留装饰侧栏，应明确记为视觉方案变更。

### P0-02：工作台静态视觉与现有正式美术仍有明显差异

- 位置：`src/presentation/brew_scene.gd:139-204,266-275`、`src/presentation/ui_kit.gd:77-98`；资源清单见 `tools/prepare_media.py:29-57`。
- 复现：当前 Windows 包进入工作台，与原版工作台截图并排比较。
- 结果：原词条栏的木框/花卉装饰和记录书的书页/花卉主体被通用浅纸面、纯色矩形及普通文字替代；原按钮装饰也变为通用矩形。四种原料在托盘中明显缩小，不再接近原版主体占比。
- 原料的具体实现差异：当前按 `cell_w * 0.44`、`shelf_height * 0.50` 设置图标框，直接 contain 整张 1024×1024 图；旧版 `scripts/ui/landscape/MerchandiseArt.lua:8-11` 使用各原料主体 frame，再由 `BrewArt.DrawIngredient` 适配可见主体。只复制原图和 alpha 全范围不能保证主体占比一致。
- 依据：P0 是迁移标题、主页、工作台的静态视觉；方案要求保留现有美术主体、构图和纸面风格。这里不要求像素一致，也不要求 P0 提前接入分类、检索或订单业务。
- 证据：[本轮包工作台](D:/p0-acceptance-20261019/brew-1280x720.png)、[本轮宽屏工作台](D:/p0-acceptance-20261019/brew-1600x720.png)、[原版工作台](../../../docs/宣传素材/2026-10-18/03-炼药工作台-实机存档.png)。
- 处理建议：接入已确认的托盘/记录书与按钮美术，按已有 source frame 校正原料主体大小；提交同分辨率对照图。若通用纸面只是占位，应将“静态视觉迁移完成”的勾选改为待完成。

### P0-03：纸条拖拽表现尚未实现，提示与可操作行为不一致

- 位置：`src/presentation/word_slip.gd:106-116`、`src/presentation/brew_scene.gd:148,207-218`。
- 复现：在工作台按住任意纸条并拖到锅上。
- 结果：WordSlip 只在按下时发出 selected；没有鼠标/触屏移动处理、Godot 拖放回调、拖拽预览或锅上落点反馈。锅的 mouse_filter 为 IGNORE。界面却提示“点选，或拖入药锅”。
- 依据：P0 计划写明纸条“点击/拖拽使用 token_id”及“验证尺寸、基线、拖拽热区”。可以不提交业务、不扣库存，但仍应提供可验的演示拖拽表现与热区。
- 处理建议：补充只影响表现的拖拽演示、预览与取消/目标外释放反馈，并携带 token_id；正式投料事务仍留在 P2。删除提示只能消除误导，不能单独满足已列出的 P0 拖拽验收项。

### P0-04：自动检查尚不能支持“完整物件框与安全区验收通过”

- 位置：`tests/integration/test_layout.gd:49,64-67,77-83`、`tests/integration/test_scenes.gd:24-43`。
- 现有测试检查 safe rect 原样返回，检查图层 width/height；报告 expected/runtime 也只有尺寸。没有比较各物件位置、旋转后的框与实际点击区域，没有把非零安全区注入真实场景并断言主要按钮在安全区内。
- 场景测试确认能装配、存在锅/托盘等节点，不覆盖上述约束。测试 PASS 不代表安全区与触控已经通过。
- 本轮另加忽略目录内的只读诊断，装配 1920×1080、2412×1080 三个场景并记录按钮/主页热区；纸条标签在 54/124/300 最大宽度下都位于纸面内。该诊断仍没有真实安卓安全区或触控证据。
- 处理建议：补预期位置/框和旋转热区的独立断言，给实际场景提供可注入 safe rect；覆盖刘海/导航区与窗口变化。随后仍需真实手机验证。

### P0-05：主页门外海港背景的缩放、定位与室内前景不匹配（用户实测）

- 来源：2026-10-19 用户提供 Godot Windows 包与原版主页两张红框对照图，并明确指出门外画面仍有问题。
- 结果：对照同一门洞及门槛，Godot 版远山、城镇和塔楼整体偏低，天空占比增大；原版门外保留的开阔海面在 Godot 版被山城挤占，独立商船与水面的空间关系也不一致。室内物件尺寸恢复后，这一门外构图差异仍然存在。
- 证据：[用户 Godot Windows 截图](p0-user-feedback-2026-10-19/home-godot-windows-user.png)、[用户原版对照图](p0-user-feedback-2026-10-19/home-original-user-reference.png)。两张附件均原字节归档，保留用户红框与标注；画面尺寸与窗口边框不同，未将直接像素差作为定量结论。
- 相关位置：`src/presentation/home_scene.gd:39-46` 的海港底图按整个 viewport cover 绘制；`src/presentation/home_layers.gd:74-79` 的室内图层按独立 content 区域缩放与定位。该变换差异是后续排查点，尚未通过修改与重测确认全部根因。
- 与 P0-01 的区别：P0-01 是超宽屏两侧延展问题；本项是门洞内部的海港、海面、码头、商船与室内前景的相对构图问题，普通窗口同样需要检查，不能只去掉侧栏就关闭本项。
- 验收要求：按原版门框/门槛对齐后比较塔楼、山城、海面范围及商船相对水面的位置；校正门外背景的设计坐标、缩放、偏移和裁切，并在 16:9、19.5:9、20:9、2412×1080 下复核。室内前景及独立物件不得为了迁就错误背景而整体挪位。
- 状态：**用户实测确认存在，待修复、待复验**；本次只追加记录与原始截图，没有修改渲染代码或重建包。
